## 상태별 실제 의미

| 경로 | 반환 rows | lastLedgerStatus | cache 변화 |
|---|---|---|---|
| 새 조회·변환 성공, 사용 가능 행 있음 | out | ok | out과 완료 시각 저장(:44–46) |
| 새 조회·변환 성공, 사용 가능 행 없음 | [] | empty | 빈 배열도 완료 시각과 저장(:44–46) |
| 유효한 비어 있지 않은 cache | cache.rows | cached | 기존 cache 유지(:28) |
| 유효한 빈 cache | [] | empty | 기존 cache 유지(:28) |
| query 또는 변환 try 블록 예외 | [] | error | 실패 결과를 저장하지 않고 기존 cache도 지우지 않음(:47–50) |

`empty`는 **SQL이 반환한 원시 행 수 0만** 뜻하지 않는다. `:41`에서 한국어 기본 이름(nm)과 값(v)이 있는 행을 거른 뒤 out.length로 정한다. 원시 행이 있어도 usable 행이 없으면 empty다. 주석의 “행 0”은 반환되는 사용 가능 행 기준으로 읽어야 한다.

SQL 조건은 frame 종류·pricing 절·평균 가격대 label·숫자 포함 값이며, 한국어 이름과 별칭을 가져온다(:30–43). “12종”은 과거 설명이다. 이번 코드가 현재 DB에서 12행을 읽었다는 증거나 SQL의 고정 행 제한은 아니다.

기본 TTL은 600,000ms(:20)다. 성공한 빈 결과도 이 기간 동안 캐시되므로 `empty`만으로 현재 턴에 DB를 다시 조회했는지 알 수 없다. `cached`는 지금 구현에서 비어 있지 않은 cache에만 붙는다. 필요하다면 결과 상태(ok/empty/error)와 자료 출처(cache/새 조회)를 별도 축으로 기록해야 한다.

실패는 negative cache로 저장하지 않는다. 유효 cache가 있으면 조회 자체를 건너뛰고, 만료 후 조회가 실패하면 해당 호출은 []를 반환한다. 기존 만료 cache가 남아 있어도 그 실패 분기에서 낡은 rows를 대신 반환하는 fallback은 없다. 다음 호출은 TTL 조건에 따라 다시 조회할 수 있다. 동시 miss 호출을 하나로 합치는 in-flight promise도 이 파일에는 없다.

## PL1 — rows와 상태가 요청 단위로 묶여 있지 않다

`lastLedgerStatus(:19)`는 모듈의 공유 가변 값이다. `priceRangesFromLedger`는 rows만 반환한다. `chat.ts:1318`은 그 반환을 await하고 블록을 만든 뒤, `:1319`에서 별도 getter로 마지막 상태를 읽는다. 따라서 반환값과 상태의 동일 요청 귀속이 함수 계약으로 보장되지 않는다.

단지 global이라는 이유만으로 실제 오염을 단정하지 않는다. 다음은 await 경계를 통과하는 **허용 가능한 작업 순서의 조건부 설명**이다.

1. A와 B가 cache miss로 서로 다른 query promise를 기다린다.
2. 두 query의 continuation 작업이 소비자 continuation보다 먼저 큐에 올라 `Q_A`, `Q_B` 순서로 대기한다고 하자.
3. `Q_A`가 성공해 rows A·cache·status=ok를 정하고 async 함수의 반환 promise를 해결한다. 이때 `chat A`의 await 뒤 작업은 이미 대기한 `Q_B` 뒤에 놓인다.
4. `Q_B`가 예외를 받아 status=error와 []를 반환한다.
5. `chat A`가 rows A로 비어 있지 않은 블록을 만들고 공유 상태를 읽으면 B의 error를 기록할 수 있다.

이는 해당 큐 순서에서 코드가 어떻게 동작하는지를 추적한 것이다. 실제 PostgreSQL 드라이버/운영 요청에서 그 순서가 발생했다는 증거를 읽거나 실행하지 않았다. 반대로 모든 환경에서 항상 상태가 섞인다는 주장도 아니다. 호출 결과가 rows/status를 한 반환 객체로 제공하면 이런 외부 스케줄링 가정에 의존하지 않고 귀속을 보장할 수 있다.

권고 계약은 예를 들어 `{rows, outcome:'ok'|'empty'|'error', cacheHit:boolean}`처럼 결과와 상태를 함께 돌려주는 것이다. 호출자는 같은 객체로 블록과 로그를 구성한다. 이 제안은 연구 설계이며 본 감사에서 서비스 구현을 수정하지 않았다.

## 관측 해석과 후속

- 새 코드의 empty/error 구분은 단일 호출의 순차 실행에서는 분명하다. error를 empty와 같은 뜻으로 보고하지 않아야 한다.
- 현재 empty는 “쓸 수 있는 반환 행 없음”이며, 캐시 여부·원시 조회 행 수·필터로 빠진 수는 제공하지 않는다.
- 초기 공유 상태 empty는 미조회라는 별도 상태를 갖지 않는다. 확인한 chat 소비자는 await 후에 읽으므로 초기값 자체가 곧 그 턴의 기록 오류라는 주장은 하지 않는다.
- 각 호출의 rows·outcome·cacheHit를 결합하고, 담당자 검증은 fresh-ok/fresh-empty/cached-ok/cached-empty/error 및 겹친 호출의 결과 귀속을 구분하는 것이 적절하다. 이 검증을 여기서 실행하지 않았다.
- 상태는 원장 자료 획득의 기록이다. 최종 모델이 그 자료를 받았는지·답에 사용했는지는 별도 주입/소비 경로 증거가 필요하다.

마감 가능한 것은 “상태 기록 추가 및 각 분기 확인”이다. 요청별 상태 귀속, 빈 캐시 출처 구분, 실제 운영 자료 수·실패·재시작·품질은 이 소스 검사로 완료 처리하지 않는다.
