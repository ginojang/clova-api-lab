## 남은 상태·판정 관측

**원장 결과와 상태를 같은 호출 결과로 반환할 필요가 있다.** 현재 함수는 rows만 반환하고 `lastLedgerStatus`를 모듈 전역으로 바꾼다. chat은 rows를 await한 뒤 별도로 이 상태를 읽는다. 겹친 두 호출의 query continuation이 소비자 continuation보다 먼저 실행되는 순서에서는 A의 rows와 B의 status가 한 이벤트에 들어갈 수 있다. 이는 가능한 소스 흐름이며 실제 운영에서 섞임·DB 오류·가격 데이터 오염을 관측했다는 주장이 아니다. `{rows, outcome, cacheHit}`처럼 결합하면 스케줄링 순서와 무관하게 그 호출의 상태를 기록할 수 있다.

또한 empty는 필터 후 쓸 수 있는 행이 없다는 뜻이며, SQL 원시 행 0만을 의미하지 않는다. 새 조회의 빈 결과와 빈 캐시 적중이 모두 empty다. 결과 상태(ok/empty/error)와 출처(cache/새 조회)를 분리하면 오류·자료 부재·캐시 재사용을 비교할 수 있다. `ver=자산 md5+행 수`는 설명대로 구현됐지만 원장 내용의 해시는 아니다.

**가격 이벤트는 아직 yes+기존 근거 없음 분기에만 있다.** `asksPriceP`는 verdict만 남기고 모델/프롬프트 판·unknown 사유를 버린다. 기능 off/nonHuman·소비 대상 아님·no·unknown·RAG 중복은 해당 가격 이벤트로 분리되지 않는다. 공통 judge 표본은 보완 근거지만 모든 턴에서 수집되는 것은 아니므로 로그 부재를 no로 읽지 않는다. 최소한 미호출/판정값/불명 원인/제외 사유를 같은 턴의 결정 기록으로 남기는 후속이 필요하다.

판정 시작 조건은 feature on·human뿐이다. 자산 주석의 “elda·가격 근거 없을 때만 묻는다”는 소비 조건보다 좁은 설명이다. 의도한 병렬 선행 호출이면 실제 범위에 맞게 설명하고, 불필요한 범위를 제한할 경우 이미 아는 자격 조건부터 적용한다. 실제 추가 호출 수나 비용은 측정하지 않았다.

## 담당 후속과 현재 마감 범위

2. 가격 결정의 yes/no/unknown/미호출·기존 근거·위기 억제·최종 소비 단계 구분. 일반/serve 두 레인에서 추가 요약이 제외되는지 확인.
