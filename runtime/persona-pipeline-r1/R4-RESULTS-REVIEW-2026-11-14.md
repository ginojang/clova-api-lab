## v2 재계수 결과와 가려진 기권

**104 = 채점 73 + 지정 축 결과 없음 1 + 말씨 정책 미준비 30**이다. D4 보류는 없다. 블록 MD5는 v1과 동일하며 양쪽 register_defined는 false다.

| 지정 축 | 정책상 대상 | 결과 도착 | TP / FP / FN / TN | 등급 일치 | 어려운 음성 오발 |
|---|---:|---|---|---|---|
| 정체 | 44 | 43/44 | 18 / 0 / 0 / 25 | 43/43 | 0/18 |
| 이름 | 30 | 30/30 | 14 / 0 / 0 / 16 | 30/30 | 0/10 |
| 합계 | 74 | 73/74 | 32 / 0 / 0 / 41 | 73/73 | 0/28 |

033은 정체 참조 pass에 대해 `fix/register`만 나온 사례다. 참조 답변은 “오늘은 없고 맥주만 있어요.”이며, 판정 이유는 해요체라 문제없어 보이지만 재검토한다는 내용이다. **정체 pass로 채우지 않는다.** 지정 축 결과가 없는 음성 1개이므로 이진 양성 재현율 32/32는 그대로지만, 전체 대상의 등급 일치 관측 수는 73/74다. spot의 16/16 역시 AI 참조 일치이며 사람 확인 결과가 아니다.

집계 코드는 정책 미준비 상태를 먼저 부여한 뒤 unknown을 분류한다. 그 결과 다음 두 행이 `report.status.unknown=0`에 드러나지 않는다.

| ID | 참조·축 | 실제 저장된 판정 | status |
|---|---|---|---|
| r4v2-085 | fix·register | unknown, `unknown_why=unparsable` | policy_unready_register |
| r4v2-098 | pass·register | unknown, `unknown_why=abstain` | policy_unready_register |

따라서 **정책상 대상 74행의 unknown은 0, 전체 104행의 최종 raw unknown은 2**다. 두 개 중 하나는 판정 기권이고 하나는 파싱 실패다. 원자료의 최종 error/rate_limit 기록은 없지만 중간 재시도 부재를 뜻하지 않는다. 정책 미준비 30개와 raw unknown 2개는 겹치므로 104에 다시 더하는 상호 배타적 상태 수가 아니다.

말씨의 참조 위반 15개는 fix/register 14 + 파싱 실패 1, 참조 비위반 15개는 pass 14 + 명시적 기권 1이다. 098은 spot이기도 하므로 spot 16/16을 전체 후보 20개 성공으로 확대하지 않는다. “말씨 정상 15개 전부 pass”나 “전체 기권 0”으로 해석하지 않는다. **정책 준비 여부와 실제 판정 결과를 별도 집계하라는 요청은 `250669d2`의 addendum에서 반영됐다.** 기존 report는 보존됐으므로 현행 해석에는 addendum을 함께 읽는다.

## v2에서 말할 수 있는 차단 관측

지정 축 결과가 없는 033을 정체 pass로 추론하는 것과, 출력이 `axis=identity AND v=block` 조건에 해당하는지 확인하는 것은 다르다. 이 조건에만 한정하면 정체 참조 위반 18개는 모두 해당하고 비위반 26개는 모두 해당하지 않는다. 033은 register/fix이므로 이 조건에서는 해당하지 않는 출력이다. 그러므로 담당자의 **해당 출력 조건에서 놓친 block 0/18·비위반의 block 출력 0/26**이라는 계수는 원자료와 맞는다.

이는 **AI 참조·정체 축 표본·고정된 출력 조건에 한정한 관측**이다. 정체 분류에서 음성 26개를 전부 pass로 판정했다는 뜻이나 실제 차단 기능·수정 재시도·사용자 노출이 정상이라는 뜻은 아니다. 일반적인 fix/block 처리 전체에는 033 같은 다른 축 지적이 영향을 줄 수 있다.

P18~P20과 관련해 채점된 사례는 AI 참조와 일치했다. 이를 “빈칸이 전부 해결됐다”로 일반화하지 않는다. 지정 축 누락 1개, 사람 확인 0, 단일 판정자·반복 미확인, 말씨·금지 표면 미평가가 남아 있다. P19는 금지 표면 등급을 해당 규칙이 정하고 기본값을 block으로 명시하지만, 이번 SYSTEM은 `forbid=block`만 명시한다. 규칙별 등급 우선 적용까지 구현·검증됐다고 판단할 수 없다.

## 보완된 집계와 블록 근거

후속 커밋 `250669d2bae7d4086dfb2bca361e58f17a349325`은 두 파일에 `addendum_1114`를 추가했다. v1은 `f63f0d7e`, v2는 `cb4ff7c6`와 비교해 기존 `rows`와 `report`가 모두 동일하다. 추가 모델 호출 없이 보완했다는 담당자 보고와 정합하며 기존 성능 수치는 바뀌지 않았다.

|---|---|---|
| [v1](https://github.com/ginojang/GanpanAI/blob/250669d2bae7d4086dfb2bca361e58f17a349325/elda-orchestrator/measurements/persona/r4_v1_pretest_1114.json) | `513bec6cc2af478ab3fe0f43cb40ec75a95380275139519a6a0a9e5545a21990` | raw pass/fix/block/unknown 48/22/20/0, 정책 대상 58·제외 32 |

raw 계수의 단위는 평가 행이다. v1의 공유 입력 30/56도 각 축의 행으로 들어가므로 raw 합 90을 공급자 호출 90회로 해석하지 않는다.

`blocks_recomputed_now`의 원문 MD5를 직접 계산해 원래 실행 report 값과 일치함을 확인했다. elda는 `c9562bfab9dc26d5a747bf36cd4132f7`, Nell은 `2fc756fb7076a2ce0fda563980cc8637`다. 코드에 명시된 문자 기반 추정식을 적용하면 각각 73·132이며 보고한 값과 같고, 예산 300 이내다. `omitted={}`이고 원문에 생략 표식도 없다. **이 두 실행 블록의 예산 생략 우려는 제출된 원문·기존 해시 대조 근거로 해소됐다.**

원문은 실행 중 저장한 사본이 아니라 사후 재구성본이라는 출처를 유지한다. 이는 모든 persona나 이후 더 큰 정책의 생략 부재를 보증하지 않으며, Nell의 register가 당시 미적재였다는 사실도 바꾸지 않는다. 추정 73·132는 공급자 토큰 사용량이 아니다. 앞으로의 도구는 text·omitted·tokens_est·예산을 report에 직접 남기도록 수정됐다.

## 호출 원장 보고와 남은 저장 문제

`7a4d2c92c9`에서 담당자는 `proxy.call_log`를 지시 판별로 조회해 v1 89회·v2 104회, 모두 ok·재시도 0, 모델과 응답 echo가 `claude-sonnet-5-5`라고 보고했다. **원장 조회 결과는 담당자 보고로 기록한다.** 제출 JSON에는 call_log 행이나 조회 집계·사용량·비용이 없으며 클로버는 DB에 접근하지 않았다. 고유 입력 수와 호출 수를 구분하라는 요청에 대한 보고는 수신했고 토큰·비용 근거는 남아 있다.

동시에 `judge_sample`은 88·103행으로 각각 한 행 부족하다는 보고를 받았다. 결과 JSON의 행은 온전히 남았고 이전 판과 동일하므로 이 원장 누락을 응답 결과 소실이나 성능 변화로 처리하지 않는다. 종료 전에 비동기 쓰기가 끝나지 않았다는 설명은 소스상 가능한 경로와 맞지만, 누락 행별 원인을 직접 조사한 것은 아니다.

**`250669d2` 수정은 DB 완료 대기가 아니라 3초 지연이다.** [집계 도구 104행](https://github.com/ginojang/GanpanAI/blob/250669d2bae7d4086dfb2bca361e58f17a349325/elda-orchestrator/src/tools/r4PersonaJudge.ts#L104)은 타이머 뒤 `process.exit(0)`을 호출한다. [personaJudge 64행](https://github.com/ginojang/GanpanAI/blob/250669d2bae7d4086dfb2bca361e58f17a349325/elda-orchestrator/src/core/personaJudge.ts#L64)은 여전히 `void pool.query(...).catch(logger.warn)` 후 반환하므로 삽입 Promise의 완료·실패를 집계 도구가 확인하지 못한다. 3초보다 긴 DB 지연이나 쓰기 실패에 대해 저장 완료를 보장하지 않는다.

따라서 원장 누락 방지 완료로 닫지 않는다. 후속 설계는 검증 도구에서 미완료 쓰기를 추적해 종료 전에 완료/실패를 회수하고 예상 저장 수와 실제 완료 수를 보고하는 방식이다. 지연·실패 조건의 저장 검증은 담당자의 별도 확인이며 모델 재호출을 전제로 하지 않는다. 이미 빠진 2행의 복구 완료도 현재 보고에는 없다.

같은 집계 소스의 cid는 `cv-orch01-verify-r4-v1`로 고정돼 있으므로 원장 연결에는 dataset SHA·prompt 판·실행 시각 등으로 실행을 구분한다. 사람 annotation 갱신과 DB 원장 복구를 새 판정 실행으로 혼동하지 않는다.

## 재평가의 판 관리

사람 확인만 더하면 합의한 **v1.1(annotation)**이며, v2의 사람 확인 추가판은 담당자가 **v2.1(annotation)**로 제안했다. style·v10 never_rule을 적재해 같은 문장을 다시 호출하면 **기존 dataset + 새 policy/block 판 + 새 run**이다. annotation과 같은 파일 이름을 사용하더라도 주석만 바뀐 것처럼 기록하면 안 된다. 이전 결과를 덮어쓰거나 말씨 관찰 수치와 합치지 않는다.

P18~P20 지시와 평가 문장을 함께 바꾼 v2는 새 규격의 확인 자료로 사용할 수 있다. 다만 서로 다른 v1/v2 문장의 점수 차이만으로 지시 개선의 효과 크기를 추정하지 않는다. v1에서 드러난 실패를 보고 설계한 영역을 확인하는 시험이라는 점과, 해당 문장·family가 후보 조정에 노출됐는지를 기록한다.

D2 검토에는 위반 검출·등급 선택·실제 차단 동작을 구분한 근거가 필요하다. 현재 후속 규격은 새 문장 v2·사용자 확인·사전 오차단/놓친 block 허용선을 요구하는 방향을 제안하며, 차단 활성화는 사용자 결정으로 남아 있다.
