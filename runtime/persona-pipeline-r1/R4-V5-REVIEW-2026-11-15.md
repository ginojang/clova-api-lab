## 인용 검토와 개봉 뒤 코드 보완

block 89개는 인용이 모두 비어 있지 않고 **정규화 전에도 해당 답의 정확한 부분문자열**이었다. 저장된 답·질문·인용의 최대 길이는 각각 UTF-16 36·23·29단위다. 이 자료는 답 3,000단위 절단·인용 120단위 절단 경계에 도달하지 않았으며 no_quote 변환도 없다. 따라서 앞서 지적한 세 코드 한계가 이번 저장 결과를 바꾼 증거는 없다. 인용 존재는 의미 판정의 타당성을 보증하지 않는다.

[35658dd0 소스](https://github.com/ginojang/GanpanAI/blob/35658dd081dcb2b717db28f0cb96001904356d04/elda-orchestrator/src/core/personaJudge.ts)를 3f88e7fc와 비교했다.

- 답의 제시·인용 검사가 모두 `ANS(answer)`의 앞 3,000단위를 사용한다. 범위 불일치 지적은 소스상 해소됐다.
- `quoteFull` 전체로 검사한 뒤 `quote`를 표시용 120단위로 제한한다. 접두만 검사하던 지적도 해소됐다.
- 인용 실패 시 원등급 `rawV`를 유지하고 DB note의 `raw:`·R4 `judged_raw_v`에 기록한다. 빈 인용은 `no_quote_empty`로 분리한다. 검사 전 등급 보존은 보완됐다.
- **전체 원인용의 영속 보존은 별도다.** 파서의 실패 반환 객체에는 quoteFull이 있으나 R4 행·DB note에는 여전히 표시용 quote만 직렬화한다. 120단위보다 긴 인용 실패를 나중에 재검토하려면 전체 인용 저장이 추가로 필요하다. v5는 최대 29단위라 이 한계에 해당하지 않는다.

**전체 원인용 저장도 후속 `62ad5b854b6d1341331e1cfb315e40890c8b9837`에서 보완됐다.** `0b35cbaf07`을 받고 [판정 소스](https://github.com/ginojang/GanpanAI/blob/62ad5b854b6d1341331e1cfb315e40890c8b9837/elda-orchestrator/src/core/personaJudge.ts)와 [R4 도구](https://github.com/ginojang/GanpanAI/blob/62ad5b854b6d1341331e1cfb315e40890c8b9837/elda-orchestrator/src/tools/r4PersonaJudge.ts)를 비교했다. 정상 pass/fix/block도 quoteFull을 반환하고, 원장 note의 q에는 quoteFull, R4 행에는 `judged_quote_full`을 저장한다. 표시용 120단위 quote는 별도로 남는다. 앞선 세 P22 코드·기록 지적은 **정적 소스 검토 기준으로 해소**됐다. 실제 DB 저장·배포·새 실행을 확인한 것은 아니다.

지시 MD5는 always `f195455a72d398ba193b3ef69781cf30`·never `281a1b86ae4236e5eb914c6598416275`로 그대로이고, v5 결과 파일도 35658dd0와 바이트 단위로 동일하다. 파서 코드 판은 달라졌으므로 prompt 판과 실행 소스 판을 모두 기록한다. 담당자의 단위 확인 4/4는 보고로 남기며 클로버의 테스트 실행으로 표시하지 않는다. 보완 후 실제 라이브 오류율은 앞으로 측정한다.

소유자가 명시적으로 보류한 always 지시 변경을 이번 작업의 미완료 구현으로 요구하지 않는다. “근거를 못 고르면 pass/abstain”의 모호성은 다음 지시 수정 때 검토할 항목으로 남긴다. v5 성능을 P22 단독 효과로 설명하지 않는다(P20·P18·출력 한도도 함께 바뀜).

## R1·R2 장애 보고와 R4의 구분

풀스택 `9d54e7fd5d`는 `/v1_0/turn/before` IP 제한으로 ratelimit.block 793줄, hookFailed를 완료로 센 R1 job 437개가 19초에 빈 답으로 지나갔다고 보고했다. 재실행·요청 속도 제한을 예고했으나 완료 근거는 아직 없다. 숫자·원인·실서빙 영향 없음은 담당 보고이며 클로버가 로그를 직접 조사한 것은 아니다.

R4 도구는 `judgePersona`를 직접 부르므로 R1·R2 before 훅과 같은 요청 경로라고 볼 수 없다. 공유 IP만으로 R4도 429를 맞았다고 판단하지 않는다. v5의 202시도·재시도0·운영 실패0은 제출 결과와 맞는다. 다른 레인 전체의 무영향 보장도 아니다. 경로·제한 키·시각·실제 429가 확인되기 전 일괄 재실행을 요구하지 않는다.

R1·R2의 무효 결과는 원본을 보존하고 유효 성능 집계에서 제외한 이유·job/조건을 남긴다. 재실행 시 대화 초기 상태·판·입력·조건별 수를 맞추고 실패 시도·시간·비용을 전체 운영 집계에서 지우지 않는다. 종료·응답 도착·훅 성공·평가 가능을 각각 기록한다.

`memory.write_degraded … store:prod`는 성공적인 운영 기억 쓰기의 증거가 아니다. 부분 성공·실패·대체 경로·principal 격리를 소유자가 확인해야 한다. 이 보고만으로 데이터를 삭제하거나 저장소 정리를 수행하지 않는다.
