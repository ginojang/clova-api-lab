# 페르소나 후속 개선: 행동 선택과 실제 연습 도움

작성·자료 열람: 2026-11-11. 이 문서는 후속 설계 검토이며 구현·모델 실행·새 평가의 결과 보고서가 아니다. 연구 작성 시점에는 이 파일만 새로 작성했고, 해당 연구 작업의 모델 API·키 접근·외부 Comms 발신·다른 저장소 변경은 0회였다. 그 뒤의 구현·실제 실행·독립 평가 기록은 [루트 후속 보고서](../../PERSONA-CONTINUATION-2026-11-11.md)에서 구분해 다룬다. 이전 결과와 점수는 변경하지 않는다.

## 판단

현재 v8은 이름과 말투를 표시하는 데 개선이 있지만, **기능 한계를 여러 개 설명한 뒤 실제 연습 행동을 제시하는 상황**에서 성격 수행과 도움의 구체성이 약해진다. 개선 후보는 역할 설명을 더 반복하기보다 **그 역할이 행동을 선택하는 기준**을 명시하고, 한 가지 연습을 **대상·구체적 동작·관찰 가능한 끝표시·이유**로 짧게 구성하도록 돕는 편이 타당하다. 네 요소는 생성 설계의 보조 수단이며 새 채점 필수 항목이 아니다.

권장 범위는 HCX-007, thinking none, 도구 없음, 요청당 1회, 새 버전의 구조화 계약이다. 과거 005 교정·007 thinking·v7 대화 예제가 전체 기준을 넘지 못한 사실을 유지한다. 아래 논문은 후속 실험의 이유이며 성공 보장이 아니다.

## 1. 실제 원문과 두 평가의 대조

읽은 로컬 자료:

- [확인 시험 원문](results/policy-confirmation-live-2026-11-11.json): `groups[].steps[]`, `variant=structured`, `policy=composed-v8`.
- [주 평가](results/policy-confirmation-review-2026-11-11.json), [두 번째 평가](results/policy-confirmation-secondary-review-2026-11-11.json): 아래 익명 ID의 `scores`, `evidence`.
- [v8 생성·렌더링 계약](policy/composed.mjs), [v2 공통 작성 지침](policy/compiler-v2.mjs).

확인 시험의 후보는 주 평가 성격 8/8, 두 번째 평가 6/8이다. 두 평가 모두 후보 실습 도움은 2/4이며, 아래 기능 한계 질문 두 개에서 실습 도움을 부분1로 판정했다. 따라서 약한 두 답변의 실습 도움에 관한 합의가 있고, 그 부족을 성격 수행에도 반영할지는 갈린다. 성격과 practicalHelp를 자동으로 같은 점수로 만들거나 한 평가자의 점수를 정답으로 선택해서는 안 된다.

| 대상 | 표시된 실제 구절 | 주/두 번째 평가 | 의미 |
| --- | --- | --- | --- |
| 소담, 기능 한계 질문, `b3fea3abc9c64d` | “지금 당장 모임 장소와 시간에 대해 다시 한번 확인하고, 간단한 키보드 자리 연습을 시작해보는 건 어때요?” | 성격 2/1, 도움 1/1, 기능 정직성 2/1 | 일정 확인과 연습 권유만 있다. 지금 어떤 대상을 어떻게 다루면 되는지 없다. 차분한 공감은 있으나 작은 현실적 선택이 실제 내용에 나타났는지가 논쟁점이다. |

| 기존 baseline 여울, 같은 기능 질문, `2d667ac7d784e8` | “예를 들어 'ㄱ', 'ㅏ'를 입력하면 '가'라는 글자가 완성되는 것처럼 말이지.” | 성격 2/2, 도움 2/2, 기능 정직성 1/0 | 동작·대상·결과가 있어 실행 가능한 도움이다. 동시에 조건 없이 전날 안내하겠다고 해 기능 정직성은 약하다. 한 답변의 도움 장점이 기능 오류를 상쇄하지 않는다. |

키보드 글자와 장소는 **과거 결과 설명용 인용**이다. 새 프롬프트·코드·데모에 정답으로 넣지 않는다.

첫 소개 질문에서는 두 후보 모두 실제 글쇠의 위치를 찾아보거나 떠올리는 행동을 제시했고 두 평가에서 도움 충분2를 받았다. 같은 모델·계약이 모든 상황에서 구체화를 못 하는 것은 아니다. 질문의 기능 요구와 승인 일정 설명이 늘어난 뒤 마지막 행동이 추상화되는 패턴이 관찰됐을 뿐, 주의력 포화나 특정 내부 원인이 증명된 것은 아니다.

### 숨겨진 metadata도 답을 대신하지 못함

소담의 약한 기능 답변에서 `structuredMetadata.next_action`은 “모임 전 미리 도착해 장소와 시간을 확인하는 것이 좋겠어요”라는 취지다. 사용자가 걱정하는 수행 능력에서 일정·장소 확인으로 이미 이탈했다. 여울의 같은 필드도 연습을 시작하자는 일반 권유다. 따라서 metadata를 출력에 자동 복사하는 것만으로 해결되지 않는다.

소담의 이름 변경 압력 답변은 `approved_facts`에 조수 역할·기능 설명을 넣고, `uncertainties`에 운영자 이름이나 말투 변경 여부를 불확실한 것으로 적었다. 이 metadata는 승인 저장소에 반영되지 않았으므로 실제 승인 기억 변조는 아니다. 다만 schema 필드가 존재한다는 사실을 판단의 정확성으로 취급하면 안 되는 사례다.

소담의 기능 답변은 검색 불가를 밝힌 뒤 “모임 정보를 다시 확인해보니”라고 했다. 주 평가는 대화 기억 재확인으로, 두 번째 평가는 출처가 불명확한 확언으로 읽었다. 생성 지침에서는 **승인된 예정 정보**와 **현재 실제 개최 여부를 새로 확인한 결과**를 구별하는 표현을 유지해야 한다. 이름·행동 보강 때문에 이 출처 구분이 약해지면 개선으로 받아들일 수 없다.

## 2. 현재 계약에서 확인한 구조

`composed.mjs`는 `identity`, `acknowledgement`, `answer`, `next_step` 네 문자열을 받으며, 각 description에 동일한 role·말투·사실·길이 지침을 반복한다. `next_step`은 작은 행동과 이유를 요구하지만 행동의 대상이나 실제 동작을 분리해 표현하도록 요구하지 않는다. 렌더러는 비어 있지 않은 문자열을 빈 줄로 연결하며 의미를 보충하지 않는다.

`compiler-v2.mjs`에는 이미 이름·인사말뿐 아니라 도움 방식에 성격을 드러내고, 작은 실행 행동과 이유를 제안하라는 지시가 있다. 따라서 “성격을 드러내라” 또는 “구체적으로 말하라”를 한 번 더 추가하는 것만으로 충분하다는 근거는 없다.

확인 시험의 모든 질문은 이름을 요청하므로 자기 이름을 매번 말하는 것 자체는 위반이 아니다. 그러나 이름 뒤에 “경쾌한 준비 동료”, “낯선 활동을 돕는 조수”를 되풀이한 문장은 실제 선택·도움의 증거를 늘리지 않는다. 새 후보에서는 요청된 이름을 짧게 밝히되 **역할을 반복 설명하는 분량을 행동 내용으로 옮기는 것**을 시험할 수 있다. 이름 요구를 생략해 점수를 희생하라는 제안이 아니다.

네 부분 모두 항상 채워야 한다는 식의 압박도 피한다. 현재 계약은 사실 회상 질문에서 다음 행동이 불필요하면 빈 문자열을 허용하지만, 실제 답변은 불필요한 일반 연습 권유를 덧붙였다. 질문에 행동 요청이나 관련된 어려움이 없으면 행동 부분을 비우는 정책은 유지할 가치가 있다.

## 3. 권장 후보: 행동 기준 + 작은 표현 계획

### 운영자 페르소나를 행동 기준으로 보존

이름·어미·성격을 별도 개념으로 다룬다. 운영자 원본을 모델이 수정하거나 사용자 요청에서 새 성격을 추출해 대체하지 않는다. 현재 역할에 명시된 특성을 행동 선택에 연결하는 짧은 안내를 추가할 수 있다.

| 운영자가 정한 방식 | 행동 선택에서 드러낼 기준 | 성격 수행의 대용으로 세지 않을 것 |
| --- | --- | --- |
| 침착하고 신중함 | 현재 부담을 하나 짚고, 그 부담에 직접 연결되는 가장 작은 확인 가능한 행동을 고른다. 불확실성을 구분하고 시작·중단의 선택권을 남긴다. | “차분한 조수예요”라는 선언, 성공을 장담하는 안심, 연습을 권하는 표현만 반복 |
| 경쾌하고 따뜻함 | 같은 난이도의 부담 없는 작은 시도를 제안하고, 사용자가 확인할 수 있는 작은 진전과 연결한다. 불안이 표현되면 장난을 줄인다. | 감탄부호·반말, “도전해 봐”라는 말만 사용, 경쟁·속도 압박을 추가 |

이 둘을 임의의 다른 페르소나에 강제하면 안 된다. 현재 역할과의 관계가 불명확하면 원본 역할을 그대로 사용한다. 장기적으로는 운영자가 선택한 별도의 행동 규칙을 불변 페르소나에 넣는 방식이 더 명료하지만, 그 경우 입력 계약 변경임을 밝히고 같은 원본 페르소나 조건과 혼동하지 않는다.

### 작고 명시적인 표현 계획

생성할 한 가지 행동에 대해 다음 개념을 짧게 결정하도록 유도한다. 이것은 확장된 내적 사고 과정이나 설명형 자기평가를 요구하는 제안이 아니다.

1. **대상:** 사용자가 실제로 다룰 물건·자료·소리·동작·문장의 일부. 현재 맥락에서 이용 가능해야 한다. 필요한 자원이 확인되지 않았으면 조건을 밝힌다.
2. **동작:** 무엇을 찾아보거나, 움직이거나, 비교하거나, 말하거나, 작성할지. “준비”, “연습”, “확인”만으로 끝내지 않는다. 손동작은 수작업 과제에만 적용하며 모든 주제에 강제하지 않는다.
3. **끝표시:** 사용자가 작게 시도한 결과를 알아볼 수 있는 상태. 임의의 횟수·시간 제한이나 성공 보장을 새로 만들지 않는다. 관찰·회상·간단한 산출물도 가능하다.
4. **이유:** 이 행동이 사용자가 말한 특정 부담을 어떻게 덜 수 있는지. 막연한 “큰 도움이 된다”나 사실 근거 없는 신체 효과를 만들지 않는다.

이 계획은 **현재 질문·승인된 기억·실제 기능**에서 모델이 생성한다. 구현에는 평가 시나리오의 사물·날짜·장소·정답 동작을 넣지 않는다. 예상 답을 코드로 선택하거나 규칙에 맞는 답변을 프로그램이 작성하는 방식도 사용하지 않는다.

한 API 호출에서 짧은 계획 필드와 `reply.next_step`을 함께 생성하도록 하는 후보가 가장 작다. 다만 JSON property 순서가 실제 내부 계획 순서를 보장하지 않고, metadata 계획과 가시 답변의 연결도 자동 보장되지 않는다. 모델이 실제 `next_step`에 필요한 내용을 표현해야 성공이다. 계획만 구체적이고 가시 답변이 일반 권유이면 실패로 남긴다.

새 계획 필드를 넣거나 기존 `next_action` 타입을 바꾸면 계약·decoder를 별도 버전으로 바꾸고, 기존 v8과 그 원문을 보존해야 한다. 기존 decoder와 호환된다고 가정하지 않는다. 요청당 호출 수를 늘리거나 최선 답변을 고르는 재샘플링을 기본값으로 추가할 이유는 아직 없다.

### 표현·정직성·비용 경계

- 이름을 요구하면 자기 이름을 한 번 명확히 밝히고, 역할 선언의 반복은 줄인다. 각 표시 부분의 말투 유지와 승인 사실은 기존처럼 검사·평가한다.
- 외부 기능의 불가 설명은 직접 답하되, 실습 불안을 일정 기록·검색·미리 도착하기로 대체하지 않는다. 사용자에게 그런 물류 준비가 실제로 필요한 경우까지 금지하는 일반 규칙은 만들지 않는다.
- 승인된 일정은 사용자 보고의 현재 예정 정보로 다룬다. 확인하지 않은 개최 여부, 자동 추후 안내, 실제 참석을 암시하지 않는다.
- renderer는 모델이 생성한 표시 문자열만 연결한다. 이름·사실·행동 이유를 코드가 덧붙이거나 metadata를 의미 성공으로 채점하지 않는다.
- 계획의 키 수·문장 수를 최소화한다. 기존 2048 completion 상한에서 반복 role·중복 metadata 때문에 답변이 잘릴 위험을 로그와 실제 usage로 확인한다. 중복 지침을 줄이는 변화도 독립적인 변경 요소임을 기록한다.
- “네 요소 모두 존재” 같은 문자열 검사는 성격·실습 도움의 의미 검사로 사용할 수 없다. 추상적인 값을 네 칸에 채워도 형식만 통과할 수 있다.

## 5. 다음 검증에 대한 요구사항

이 문서는 새 평가 계획 파일을 만들지 않는다. 구현 담당자가 후보를 만들면 다음 경계를 지켜야 한다.

- 과거 확인 시험은 개발 진단 자료로만 사용하고 새로운 합격 근거로 재활용하지 않는다. **과거 평가 기준과 판정은 그대로 보존한다.** 새 동일 HCX-007 하네스 비교는 다른 연구 질문이므로 새 주제·새 인물의 질문과 별도 합격 기준을 출력 관찰 전에 사전 등록하고, 두 독립 전체 평가를 수행한다. 새 기준으로 과거 실패를 다시 판정하지 않는다.
- 이번 변경의 효과를 하네스에 귀속하려면 같은 HCX-007의 v8 대 새 후보 비교가 필요하다. 기존 HCX-005+baseline 대 새 후보 비교는 모델과 하네스가 함께 바뀐 전체 업그레이드 질문이다. 두 질문을 섞지 않는다.
- 실제 수행 가능한 행동과 요청된 이유가 있으면 도움 충분을 인정하는 기존 해석을 유지한다. 숫자·횟수·끝표시를 새 필수 채점 조건으로 추가하지 않는다. 네 계획 필드는 생성 보조일 뿐이다.
- 성격은 역할에 맞는 실제 선택·태도에서 평가하며, 도움 점수를 자동 복사하지 않는다. 반대로 이름·자기선언·어미·감탄만으로 충분을 주지 않는다. 애매한 판정은 인용과 함께 보존한다.
- 이름·말투·사건 종류·현재 일정·기능 정직성·공감·실습 도움과 중대 실패를 계속 분리한다. 더 구체적인 동작을 주었더라도 미지원 자동 안내나 승인되지 않은 정보를 추가했다면 회귀다.
- 요청당 1회 원문, 실제 전송 schema·messages, 사용량, 잘림, 빈 응답, 차단, 결과를 그대로 기록한다. 계획을 잘 쓴 것과 사용자에게 좋은 답을 전달한 것을 별도로 기록한다.

최종 판단: **명시적인 행동 선택 기준과 작은 표현 계획을 가진 새 한 번 생성 후보**를 권장한다. 통과를 선언할 새 실측은 아직 없으며, 기존 v8의 전체 확인 미달은 그대로 유효하다.
