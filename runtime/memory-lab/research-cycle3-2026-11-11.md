# 세 번째 후속 사이클: 자기 정체성의 귀속과 근거 있는 공감

조사일: 2026-11-11. 이 문서는 실제 개선을 미리 주장하지 않는 **개발 전 연구·설계 근거**다. 읽기·쓰기는 이 저장소 안에서만 했고, API 키·배포 설정·`CLAUDE.md`를 읽지 않았다. 연구 담당자는 모델 API 호출이나 외부 메시지 발송을 하지 않았다. 논문 전체를 저장소에 복사하지 않았다.

## 1. 이번에 해결할 관측과 원인 가설

지난 [두 번째 사이클 보고서](../../PERSONA-CYCLE2-2026-11-11.md)의 `slim-v10`은 같은 HCX-007의 `composed-v8`보다 말투 준수와 토큰·응답 시간에서 개선을 보였다. 그러나 이름 오류는 양 조건에 한 건씩 남았고, 두 번째 독립 평가자는 후보의 공감 한 건을 낮게 평가했다. 전체 보호 조건은 통과하지 못했다. 이 결과를 새 후보의 성공으로 재해석하지 않는다.

[첫 평가](results/policy-slim-v10-primary-review-2026-11-11.json)와 [두 번째 평가](results/policy-slim-v10-secondary-review-2026-11-11.json)의 동일 후보 응답에는 `나는 하늘이야!`가 나오고, 이어 운영자 이름 `해온`을 언급하면서 요청받은 다른 이름 `뭉치`도 수용한다. 따라서 올바른 이름이 **한 번 등장하는지**만으로는 정체성 유지 여부를 판단할 수 없다. 또한 대조 조건은 자기 이름을 밝힌 뒤 `네 이름은 여전히 ‘해온’이야.`라고 말해 이름의 소유자를 바꿨다. 이름 누락, 다른 자기 이름 선언, 사용자에게 잘못 귀속, 변경 요청 동의는 서로 다른 실패다.

[기존 guard](policy/guard.mjs)의 `identityFindings`는 올바른 자기 이름 선언을 하나 발견하면 정상으로 반환한다. 다른 이름으로 바꿨다는 고신뢰 판정은 `이제/앞으로는` 및 기존 이름 폐기 표현의 결합 등 좁은 문법을 요구한다. 이 설계는 `나는 AI야` 같은 일반 명사를 이름 오류로 잡지 않으려는 합리적 방어를 포함하지만, 이번 복수 주장 충돌을 충분히 검사하지 못한다. 후보 응답의 경고 `persona.self_name_unverified`도 의미 성공이 아니며, `ok: true`는 알려진 고신뢰 오류를 검출하지 않았다는 제한된 뜻이다.

공감 문제는 `걱정 마, 천천히 연습하다 보면 분명히 나아질 거야.`라는 표현이다. 한 평가자는 구체적 부담의 인정과 작은 행동을 높게 평가했고, 다른 평가자는 감정 축소와 근거 없는 낙관을 문제 삼았다. 새 연구를 근거로 과거 어느 평가도 지우지 않는다. 새 후보에서는 부담을 정확히 반영한 뒤 **행동의 목적**을 설명하도록 하며, 미래 성과를 보장하지 않는 쪽을 시험할 수 있다.

## 3. 기존 연구의 재확인과 API 제약

[Wallace 외, The Instruction Hierarchy](https://arxiv.org/html/2404.13208v1), §3·4·부록 A를 다시 확인했다. 비충돌 요청은 따르고 충돌 요청은 무시하는 구분을 학습시키는 연구이며, 단순 system 지시보다 학습한 방식이 강했다. 이는 **정상 요청을 과도하게 거절하는 검사를 함께 해야 한다**는 근거다. 이미 과거 연구 문서에 있으므로 새로운 논문 수에 포함하지 않았다.

[NAVER Structured Outputs 공식 문서](https://api.ncloud-docs.com/docs/clovastudio-chatcompletionsv3-so)의 요청·스키마 지원·참고를 재확인했다. HCX-007에서 JSON 구조 출력을 지원하고, 한 요청에 system 메시지는 하나다. 추론/Function calling과 동시 요청할 수 없으며 `pattern`을 지원하지 않는다. 따라서 응답 문자열의 자기 지시 대상이나 한국어 감정 축소를 JSON Schema 정규식으로 해결한다는 설계는 사용할 수 없다. 네 문자열의 형식 검증과 그 내용의 의미 검증은 구분해야 한다.

우선 A를 별도 버전으로 구현하고 B를 진단 도구로 검증하는 접근을 권고한다. C를 채택한다면 첫 호출 비교와 추가 교정 결과를 분리해 사전 고정한다. B가 오류를 발견했다고 해서 A의 생성 능력이 좋아진 것으로 집계하지 않는다. D는 채택하지 않는다. 기존 `slim-v10` 원문·판정·해시를 바꾸지 않는다.

새 지시는 `해온/하늘/뭉치`나 특정 시험 질문을 포함한 정답 예시가 아니라 임의 운영자 설정에 적용되는 원칙이어야 한다. “다른 이름으로 부를게”의 목적어는 한국어에서 모호할 수 있으므로, 그 문구만으로 도우미가 자기 이름을 바꿨다고 무조건 판정하지 않는다. 이름 확인이 필요한 답변에서는 누가 누구인지 직접 드러나는 자기소개를 요구하고, 다른 화자·역할·인용의 허용 범위를 유지한다.

## 5. 개발·확인 평가에 넣을 대조 사례

**정체성의 양성·음성 대조**를 함께 둔다. 정확한 자기 이름 뒤에 다른 이름을 수용하는 경우, 사용자에게 운영자 이름을 귀속하는 경우, `나는 AI 도우미야`처럼 일반 역할을 설명하는 경우, 다른 사람의 이름을 정확히 인용하는 경우, 잘못된 자기소개를 부정·정정하는 경우를 분리한다. 다국어·띄어쓰기·괄호가 포함된 운영자 이름도 정규식 삽입과 이름 경계를 검증한다. 제한된 문법으로 판정할 수 없으면 검출 미확정으로 남기며 완전한 의미 검증이라고 표기하지 않는다.

**공감과 실용 도움**은 따로 본다. 구체적 부담을 인정했는지, 감정을 없애라고 압박하거나 성과를 단정했는지, 요청한 작은 행동의 대상·동작·이유가 있는지를 각각 검토한다. 단순 단어 블랙리스트로 공감을 채점하지 않는다. 예를 들어 금지 표현을 비판하는 직접 인용까지 감정 축소로 집계하면 안 된다. 사용자가 행동을 요청한 사례에서 공감만 길게 쓰는 것도 성공이 아니다.

**독립 확인**에서는 개발에 쓴 질문·이름과 구별되는 새 사례를 쓰고, 두 조건에 같은 승인 기억·모델·생성 한도·요청을 제공한다. 한 번에 좋아졌다는 인상을 피하려면 이름·말투·성격·사실·능력·공감·실용 도움의 쌍별 퇴행을 유지해서 본다. 전체 합격 기준과 판정 축은 출력 전에 고정한다. 두 평가자는 조건과 서로의 판정을 보지 않은 채 원문 근거를 남기고, 특히 공감의 불일치는 그대로 보고한다.

실제 사용량·첫 응답과 최종 응답·추가 호출·차단·오류·미확정은 별개로 기록한다. 평가 한 번의 통과는 장기 페르소나 유지, 사용자 만족, 임상적 효과, 운영 배포 준비를 증명하지 않는다. 이번 문서는 그 실측을 설계하는 근거이며 결과 보고서를 대신하지 않는다.
