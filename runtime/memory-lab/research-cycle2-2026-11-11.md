# 두 번째 후속 사이클: 짧은 출력 계약과 한국어 말투 유지

자료 열람·작성: 2026-11-11. 작업 범위는 이 저장소 내부이며 이 연구 작업은 모델 API·키 접근·Comms 발신을 하지 않았다. 새 실측의 성과를 미리 주장하지 않는다. 이전 비교의 원문과 판정은 [v9 보고서](../../PERSONA-CONTINUATION-2026-11-11.md)에 그대로 보존한다.

## 1. 이번에 바꿀 가설

v9의 숨은 행동 계획 추가는 같은 HCX-007에서 성격·실용 도움을 높이지 못했고, 해요체는 8/8에서 6/8로 퇴행했다. 입력·출력·평균 지연도 각각 약 25.2%·35.0%·33.3% 늘었다. 이 관측은 **더 많은 자기보고 필드가 더 좋은 실제 답변을 보장하지 않는다**는 직접 근거다. 그러나 한 번의 소표본으로 숨은 계획이 퇴행의 유일한 원인이라고 증명할 수는 없다. 계획 필드·설명 지시·출력 길이가 함께 달라졌다.

다음 후보는 **공식 JSON 출력을 유지하되 사용자에게 표시하는 네 문자열에 생성 과제를 집중**하는 편이 낫다. 정체성·실제 기능·승인 기억은 이미 하네스가 소유하는 입력 상태다. 모델이 같은 내용을 숨은 필드로 다시 선언하게 만들기보다, 실제 답변이 해당 상태를 지키는지를 별도 평가한다. 이 선택은 아래 연구와 로컬 실패를 연결한 설계 추론이며 HCX-007의 품질 개선 보장은 아니다.

기존 [첫 후속 연구](research-continuation-2026-11-11.md)의 InCharacter·성격 행동 평가·Plan-and-Solve는 새 논문 수에 다시 포함하지 않았다. 이번에 기존 `research*.md` 목록과 대조해 새로 확인한 것은 **논문 6개, 연구자 재현 글 1개**, 그리고 재확인한 NAVER 공식 문서다. 검색 요약만으로 내용을 인용하지 않고 원문 PDF/HTML의 해당 절을 읽었다.

### NAVER 문서에서 재확인한 구현 한계

[공식 Structured Outputs 문서](https://api.ncloud-docs.com/docs/clovastudio-chatcompletionsv3-so)의 요청·지원 스키마·참고를 확인했다. 현재 문서는 HCX-007, `responseFormat.type=json`, 한 개의 system 메시지, `thinking.effort=none`을 명시하며 Structured Outputs와 추론/Function calling의 동시 요청을 지원하지 않는다. 객체 `properties`·`required`와 문자열 타입은 지원하지만 `pattern`은 지원하지 않는다.

따라서 JSON Schema regex로 모든 한국어 문장 끝을 강제하는 설계는 공식 API 기능으로 구현할 수 없다. 구조 검증과 실제 말투 의미 평가는 분리해야 한다. 자유로운 reply 문자열에 지시를 주는 것은 **형식 제약의 의미 보장**이 아니다. 새 후보도 tools none·thinking none·동일 출력 상한을 유지하는 것이 비교에 적절하다.

## 4. A 후보의 최소 계약 제안

1. 출력은 별도 버전으로 만들고 정확히 네 표시 문자열을 검증한다. 위치는 최상위 네 필드 또는 `reply` 아래 네 필드 중 하나로 먼저 고정한다. 예전 스키마를 조용히 다른 뜻으로 바꾸지 않는다.
2. 정체성은 운영자 persona에서, 실제 기능은 설치된 capabilities에서, 기억은 승인 저장소에서 가져온다. 모델 출력으로 이를 갱신하거나 누락된 값을 보충하지 않는다.
3. 역할을 말투와 구분한다. 차분함/경쾌함 같은 유형을 코드에서 임의로 추출해 다른 역할에 덮어씌우지 말고 운영자의 원문 역할을 전달한다. 이름 요구가 있으면 답변에서 이름을 밝히되 매번 역할 설명을 반복할 필요는 없다.
4. 행동 도움은 표시 `next_step`에 대상·동작·요청된 이유를 직접 표현한다. 실제 작업 도움을 일정 확인으로 대체하지 않는다. 사실만 묻는 질문이면 행동 필드는 비어 있어도 된다.
5. 해요체/해체의 좁은 지시는 운영자 설정에 해당할 때만 적용한다. 타 언어·알 수 없는 말투 설정을 해요체로 조용히 정규화하지 않는다. 모든 비어 있지 않은 표시 부분에 동일한 말투 기준을 적용한다.
6. 원문 네 부분을 그대로 연결한다. 이름 붙이기·어미 치환·행동 문장 자동 추가·정답 enum은 사용하지 않는다. 구조 오류와 빈 답변은 실패로 남긴다. 구조가 맞아도 `semanticVerified:false`다.
7. 실제 이력에는 전달된 표시 답변만 남긴다. 별도의 schema 검증이나 진단 로그를 사용자 기억으로 승격하지 않는다. 형식 변경과 이력 처리의 회귀를 scripted SDK 검사로 먼저 확인한다.

이는 생성 한 번에 적용 가능한 변경이다. 별도 writer·judge 호출이나 실패 시 자동 답변 선택을 기본 전략으로 추가하지 않는다. 추가 모델을 붙이면 다른 비용·지연 조건의 실험이 되므로 별도 비교로 취급해야 한다.

## 5. 이번 사이클에서 발전을 확인하는 방법

**개발 진단과 확인 시험을 구분한다.** 과거 키보드 도움 누락과 v9 해요체 혼용은 공개된 개발 실패 사례다. 이를 다시 통과한 결과는 결함 재현/수정 근거로 기록하고, 새 이름·새 활동·새 표현의 확인 시험을 별도로 동결한다. 개발 중 후보를 바꾸면 각 버전·실패 호출도 모두 남긴다.

새 확인 시험은 같은 HCX-007의 v8 대 후보를 비교한다. 인물·사용자 말투·승인 기억·정정·재시작·질문·출력 상한·온도·간격을 일치시키고 순서를 균형화한다. 도움 요청이 쉬웠던 한 주제만 사용하지 말고, 최소한 다른 실제 작업 맥락과 사실 회상/기능 한계의 전환을 포함한다. 대화 이력을 쌓지 않은 단발 질문만으로 지속성을 주장하지 않는다.

평가 축은 이름·말투·성격·사건 의미·최신성·기능 정직성·공감·실용 도움으로 유지한다. 성격은 자기소개나 어미만으로 통과시키지 않고 실제 선택·태도로 판정한다. 도움은 실행 가능한 대상과 동작 및 요청된 이유로 판단하며, 생성 계약의 필드 수나 특정 연습 정답을 채점 필수 요소로 만들지 않는다.

**품질 향상과 효율 개선을 별도 결론으로 사전 등록한다.** 새로운 확인 시험에서 대조군이 만점이면 ‘성격 +1’을 증명할 수 없다. 결과를 본 뒤 합격선을 바꾸지 말고, 처음부터 (a) 실제 품질 향상, (b) 보호 축 퇴행 없이 사전에 정한 토큰 절감이라는 서로 다른 판정을 정의할 수 있다. (b)만 충족하면 ‘품질을 유지하며 비용 부담을 줄였다’고 말해야 하며 ‘성격이 더 좋아졌다’고 바꾸어 말하지 않는다. 토큰 절감으로 말투 퇴행을 상쇄하지 않는다.

두 독립 전체 AI 리뷰에는 조건 이름·구현·개발 평가를 숨기고 질문·persona·승인 기억·표시 원문·동일 rubric만 전달한다. 점수 원문과 인용을 먼저 동결하고 이후에 집계한다. 집계 평균이 같아도 대응 문항의 퇴행을 숨기지 않는다. 사용량은 전체 system·schema·history 입력과 생성된 모든 출력으로 계산하고, 비용·크레딧 잔액을 조회하지 않았다면 금액은 미상으로 둔다.

현재 결론은 **공식 구조화 출력과 원문 보존을 유지하면서 생성 의무를 줄이는 A를 먼저 실측하자**는 것이다. 새 후보의 실제 성과·선택·승격은 이 문서의 연구 권고가 아니라 후속 실행 증거로 결정한다.
