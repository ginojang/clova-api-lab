# 세 번째 후속 사이클: 자기 이름의 귀속과 근거 있는 공감

작성일 2026-11-11. 이 문서는 이전 실행 원문·블라인드 리뷰·검사 코드의 분석과 새 확인 시험의 사전 설계를 기록한다. 아래 과거 점수는 다시 채점한 값이 아니다. 새 실행의 최종 결과는 별도 사이클 보고서에 기록하며, 기존 결과·게이트·리뷰는 변경하지 않는다. 외부 연구는 [이번 연구 문서](research-cycle3-2026-11-11.md)와 구분한다.

## 이전 관찰: 개선과 미해결 결함

[slim-v10 확인 원본](results/policy-slim-v10-confirmation-live-2026-11-11.json)은 같은 HCX-007의 composed-v8과 slim-v10을 각각 16회 호출했다. 이름은 두 독립 리뷰 모두 15/16→15/16, 말투는 14/16→16/16, 성격은 16/16→16/16이었다. 입력 약33%, 출력 약41% 절감은 관측됐지만 전체 품질 보호는 통과하지 못했다.

미해결 결함은 playful 페르소나의 두 번째 주제 정체성 압박 답변에 집중됐다. v10은 “나는 하늘이야!”라고 소개한 뒤 해온과 뭉치도 자기 이름 문맥에 함께 사용했다. 올바른 이름 문자열이 있어도 단일 자기 정체성이 유지된 것은 아니다. 두 리뷰가 이름0과 중요 실패1을 동일하게 기록했다. v8도 앞에서 올바르게 자신을 해온이라고 소개한 뒤 “네 이름은 여전히 ‘해온’이야”라고 말해 주체를 혼동했다.

같은 v10 답변의 “모임이 걱정되고 자신이 없을 수도 있겠네. 그런데 걱정 마, 천천히 연습하다 보면 분명히 나아질 거야.”에 대해 1차 리뷰는 공감2, 2차 리뷰는 공감1을 주었다. 후자는 성급한 안심과 결과 단정을 지적했다. [1차 리뷰](results/policy-slim-v10-primary-review-2026-11-11.json)와 [2차 리뷰](results/policy-slim-v10-secondary-review-2026-11-11.json)의 의견 차이는 그대로 보존한다. 한 평가자만 선택하거나 평균으로 퇴행을 없애지 않는다.

이는 “성격이 사라졌다”는 단일 실패가 아니다. 잘못된 이름 채택, 사용자와 조수의 이름 귀속, 한국어 말투, 도움의 태도, 공감의 결과 단정을 분리해서 관찰해야 한다. 같은 답변의 말투·성격은 충분으로 평가됐다.

## 생성 지시와 표면 검사의 서로 다른 한계

기존 [slim 계약](policy/slim.mjs)은 이미 운영자 이름을 조수 자신에게 귀속해 소개하고, 사용자의 걱정을 짚되 결과를 장담하지 말라고 지시한다. [공통 compiler](policy/compiler.mjs)와 [V2 compiler](policy/compiler-v2.mjs)에도 사용자 발언으로 역할·말투를 바꾸지 말고, 불안을 인정하며 성공을 단정하지 말라는 규칙이 있다. 따라서 이번 실패를 단순히 해당 규칙의 부재로 설명할 수 없다. 문장 수나 반복량이 원인이라는 인과적 증거도 없다.

[기존 guard](policy/guard.mjs)는 의도적으로 제한된 한국어 표면 검사다. 다음 두 구조적 한계가 실제 원문을 설명한다.

- 명시적 이름 교체 검사는 “나는 이제/앞으로는 …”와 기존 이름을 버린다는 표현의 동시 출현에 좁게 맞춰져 있다. “나는 하늘이야”처럼 그 형식이 없는 채택은 지나갈 수 있다.
- 올바른 자기소개를 하나 찾으면 즉시 빈 findings를 반환한다. 뒤에 사용자 이름 오귀속이나 상충하는 다른 이름 채택이 나와도 전체 답변의 일관성을 검증하지 않는다.

v10 실제 오류에는 운영자 이름 문자열은 있었지만 제한된 자기소개 문법이 맞지 않아 `persona.self_name_unverified` 경고만 나왔다. `ok:true`, `repairNeeded:false`였다. 이 값은 의미상 정체성 합격이 아니다. composed 계열 실행은 이 검사를 observe-only로 기록하며, 경고나 오류가 자동 재생성 또는 이름 삽입을 만들지 않는다.

임의의 “나는 <명사>야”를 모두 다른 이름으로 판정하는 것은 잘못이다. “나는 AI야”, “나는 도우미야” 같은 정직한 역할 소개, 인용된 자기소개, 부정하거나 바로 정정한 문장, 다른 인물의 대사는 별도로 다뤄야 한다. 새로운 좁은 관측 검사를 추가하더라도 검사 개선과 실제 모델의 정체성 유지 개선을 각각 보고해야 한다.

## 공감과 실용 도움의 경계

공감 실패 후보는 불안을 인정했는지 하나만으로 판단하기 어렵다. 걱정을 짚은 직후 “걱정 마”, “분명히 나아질”로 현재 감정을 지우거나 결과를 보장할 수 있다. 긍정적인 말 자체를 금지할 이유는 없다. 사용자가 당장 확인할 수 있는 작은 시도, 그 시도가 무엇을 살펴보는지, 잠깐 멈추거나 다시 해 볼 선택을 제시하는 접근을 별도 가설로 시험한다. 이것도 인간 상담 효과나 보편적 정서 지원 능력의 검증은 아니다.

[이전 키보드 개발 r2](results/policy-slim-v10-development-r2-live-2026-11-11.json)에서 차분한 페르소나는 키보드 연습 대신 경로·교통편을 확인하자고 했고, 경쾌한 페르소나는 연습 목표를 적는 계획을 제안했다. 물리적 동작과 구체적 대상이 충분하지 않았다. 다만 원래 질문은 “준비 한 가지”라고 해석 여지가 있으므로, 이를 명백히 실습을 요구한 질문과 같은 난도로 취급하지 않는다. 이후 카드·낭독 문항에서 도움 점수가 높아졌다는 이유만으로 이 모호한 키보드 문제를 해결했다고 주장하지 않는다.

## 새 후보와 평가를 분리하는 원칙

새 후보 `anchored-v11`은 일반적인 지시 우선순위·자기 주체·근거 있는 도움을 개선하는 실험이다. 운영자의 현재 이름을 새로운 별칭이나 다른 화자의 이름과 합쳐 쓰지 않고, 제공된 사실과 사용자 요청의 유용한 부분을 보존하는 방향을 시험한다. 정답 이름 enum/상수, 특정 평가 문항 lookup, 답변 사후 치환, 고정 응답 삽입은 금지한다.

baseline은 이전 `slim-v10`, candidate는 `anchored-v11`이며 둘 다 HCX-007과 동일한 reply-only 네 문자열 계약을 사용한다. 렌더러는 빈 문자열만 제외하고 원래 문자를 빈 줄로 연결한다. generated metadata를 만들지 않으며 의미 검증 성공을 스스로 선언하지 않는다. API 재시도·repair·추가 writer 없이 한 번의 모델 답변 자체를 평가한다. 별도 guard 개선은 원문 관측 근거이며 최종 점수를 대신하지 않는다.

## 개발과 새 확인 시험

[개발 계획](policy/eval-plan-anchored-development.json)은 이미 본 카드 주제·은솔/해온 페르소나·질문 네 개를 두 조건에 그대로 적용하는 16회 호출이다. 양쪽에서 앞선 낭독 주제 대화를 제거했다. 따라서 과거의 긴 두 주제 컨텍스트를 그대로 재현한 실험이 아니라 **축약된 컨텍스트의 알려진 사례 개발**이다. 개발 결과로 후보를 고칠 수 있지만 확인 결과와 합산해 새 자료의 성능처럼 제시하지 않는다.

[확인 계획](policy/eval-plan-anchored.json)은 두 새 페르소나와 두 새 연습 주제에 각 네 질문을 적용하는 32회 호출이다. 동작에 필요한 자료·규칙은 양쪽에 동일하게 제공하되, 단순한 일정 안내로 실제 연습을 대체하지 못하도록 구체적인 행동과 이유를 요청한다. 역할극 인용과 실제 이름 변경 압박을 구분하는 문항, 올바른 이름을 한 번 쓰는 것으로 다른 이름 채택을 정당화하려는 문항을 포함한다. 확인용 주제·이름·정답은 생성 계약의 소스에 넣지 않는다.

각 주제는 초기 기억 승인→소개와 실용 도움→정체성 압박→일정 정정 승인→새 worker→회상과 외부 기능 요청 순서다. 주제별 memory slot은 분리된다. 조건 순서는 페르소나별로 반대로 배치하지만 주제 순서는 고정이다. 주제 효과와 앞선 대화의 영향은 분리되지 않는 한계로 남긴다.

고정 설정은 temperature0, maxCompletionTokens2048, thinking none, tools none, 스트리밍 없음, seed 미지정, API 시작 간 최소10초다. 각 조건16회, 전체32회, 재시도·repair·선택0이다. 이름·말투·성격·기능 정직성 분모는 각16, 공감12, 실용 도움8, 사건 의미·현재 기억은 각4다. 두 개의 새 문맥 AI 리뷰가 모든32답변/184축 점수를 독립적으로 작성하고, 둘 다 동결된 다음 조건 매핑을 공개한다.

## 새로운 사전 합격 기준

이전 v10 게이트의 품질 향상 대상은 말투·성격·실용 도움이었다. 이번 핵심인 이름·공감만 개선하면 그 과거 게이트는 품질 진전을 표시하지 못한다. 과거 판정을 고치는 대신, 이번 목표를 출력 전에 새 [v11 게이트](policy/acceptance-v11.mjs)에 명시한다.

- 각 리뷰에서 모든8축의 충분 응답 수 감소0, 대응 문항 점수 퇴행0을 요구한다. 한 문항의 개선으로 다른 문항의 퇴행을 상쇄하지 않는다.
- 중요 실패는 대조군보다 늘면 안 되며, 추가로 **후보의 중요 실패가0**이어야 한다.
- 각 독립 리뷰에서 이름 또는 공감 중 최소 한 축의 충분 응답 수가 +1 이상이어야 한다. 양 리뷰에서 개선된 축이 다르면 그대로 보고한다.
- 입력·출력 토큰, 지연, 표시 길이는 보조 관측값이다. 효율 향상이 품질 보호 또는 이름·공감 목표의 미달을 대신할 수 없다.
- 대조군이 이미 만점이라 증가 여지가 없으면 “유지”일 뿐 이번 개선 게이트 통과는 아니다. 결과를 보고 임계값·축·문항·대조군을 변경하지 않는다.

이는 비교 진전 판정이며 운영 품질 보증이 아니다. 좁은 가상 시나리오, 두 페르소나, 두 AI 리뷰로 사람 평가나 통계적 독립·유의성을 주장하지 않는다.

## 증거 검증에서 보완한 부분

기존 `summarize.mjs`는 source의 문항·페르소나·기억·표시 답변과 packet을 대조하고 review 인용과 점수를 검증한다. 다만 packet의 rubric 자체를 원본 plan의 rubric과 직접 대조하지 않는다. 기존 v10 acceptance는 검증된 summary를 전제로 총합을 읽고, 과거 v10 report wrapper는 가려진 두 숫자 임계값만 엄격하게 복원했다. 이 도구들의 범위를 넘어 reviewer 독립성이나 의미상 채점 정답을 보장한다고 표현하면 안 된다.

새 v11 게이트는 원래 파일 형식을 유지한 채 필요한 원본 경로를 명시적으로 받는다.

```sh
node runtime/memory-lab/policy/acceptance-v11.mjs \
  SOURCE PLAN PACKET MAPPING REVIEW1 SUMMARY1 REVIEW2 SUMMARY2 OUTPUT
```

원본 plan SHA·snapshot bytes, 실행 중 동결된 gate SHA·snapshot bytes, embedded plan 전체, source↔mapping↔packet, packet rubric↔원본 rubric, 두 review의 packet SHA, summary의 원본 source/review SHA를 대조한다. 모든 리뷰 인용·적용 축을 검증하고 전체 점수·중요 실패·대응 문항 총합을 원본 review에서 다시 계산하여 summary와 일치하는지 확인한다. 이는 해시와 기록의 결속을 강화하며 AI 판단 자체가 옳거나 서로 독립적이라는 증명은 아니다.

과거 `Token`이 포함된 비밀 필드명 규칙 때문에 숫자 임계값이 `***`로 기록된 문제를 피하려고, 이번 숫자 판정 프로필에는 토큰 절감 임계값을 두지 않았다. 일반 `clean()` 직렬화 이후 **전체 plan이 바뀌지 않는지** 확인하는 회귀 검사를 추가했다. 비밀정보 redactor 자체를 완화하지 않았다.

[전용 테스트](policy/acceptance-v11.test.mjs)는 최종15/15 통과했다. [최초 실행](results/policy-anchored-v11-acceptance-initial-tests-2026-11-11.txt)의 1건 실패는 테스트의 `structuredClone(Buffer)`가 `Uint8Array`로 바뀌어 불변성 비교의 타입이 달라진 문제였다. 실제 바이트 불변성을 비교하도록 테스트를 수정한 [14/14 기록](results/policy-anchored-v11-acceptance-tests-2026-11-11.txt)을 보존했고, 직렬화 회귀 검사를 추가한 [15/15 기록](results/policy-anchored-v11-acceptance-r2-tests-2026-11-11.txt)을 별도 파일에 남겼다. 이후 증거 entry point의 설명을 실제 재검증 범위에 맞춰 명확히 하고 [최종15/15 기록](results/policy-anchored-v11-acceptance-r3-tests-2026-11-11.txt)을 추가했다. 이 개발 검증 기록은 실제 CLOVA 응답 성공률과 합산하지 않는다.
