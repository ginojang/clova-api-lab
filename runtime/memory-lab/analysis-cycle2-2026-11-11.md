# 두 번째 후속 사이클: v8/v9 실패 분석과 간소화 검증 설계

작성일 2026-11-11. 이 분석은 저장된 원문과 실행 코드를 읽어 작성했다. 새로운 모델 호출, 키 조회, 외부 Comms 발신은 하지 않았다. 과거 출력·평가·판정은 변경하지 않는다. 외부 논문 검토는 [별도 연구 문서](research-cycle2-2026-11-11.md)에 구분한다.

## 관찰과 인과 해석의 경계

[v9 실제 비교](results/policy-enacted-v9-live-2026-11-11.json)는 같은 HCX-007의 v8과 v9에 각 8회 요청했다. 두 독립 평가에서 이름·성격·도움 등은 유지됐지만 말투는 8/8에서 6/8로 줄었다. 숨은 계획을 추가하면 성격이 좋아진다는 가설을 이 표본은 지지하지 않는다. 다만 schema 지시와 출력 필드가 함께 바뀌었으므로, 특정 필드 또는 길이가 퇴행의 원인이라고 입증한 실험도 아니다.

## 중복과 비용의 정량 분석

아래 문자 수는 저장된 API context의 `responseFormat`과 응답을 Python `json.dumps(..., ensure_ascii=False, separators=(',', ':'))`로 직렬화해 센 Unicode 문자 수다. raw 출력·표시 답변은 저장된 문자열 길이다. 토큰 분해치가 아니며 JSON 직렬화 길이와 실제 네트워크 바이트도 다르다.

| 8응답 합계 | v8 | v9 | 관측 |
| --- | ---: | ---: | --- |
| schema 문자 | 37,186 | 54,210 | +45.8% |
| 실제 system 문자 | 24,520 | 24,520 | 동일 |
| raw 출력 문자 | 6,428 | 8,636 | +34.4% |
| 표시 답변 문자 | 2,296 | 2,237 | -2.6% |
| reply를 제외한 metadata JSON 문자 | 3,504 | 5,657 | raw 대비 약 54.5%→65.5% |
| support_plan JSON 문자 | 없음 | 1,984 | 사용자에게 표시되지 않는 추가 출력 |
| 비어 있지 않은 표시 부분 | 32/32 | 32/32 | 선택적 부분도 모두 채움 |
| 대략적 표시 문장 수 | 72 | 66 | 평균 9→8.25문장 |

문장 수는 `. ! ? 。 ！ ？` 뒤 공백에서 분리한 기술적 근사치다. 운영자 2~4문장 지침에 비해 양쪽 모두 장황했다. 이는 개발 진단이며, 기존 rubric에 없던 새 길이 축으로 과거 점수를 바꾸지 않는다.

각 응답 schema 안에 운영자 role 전문이 v8은 4번, v9는 5번 들어갔다. system 안에도 한 번 들어갔다. v8/v9 모두 표시 필드마다 동일 공통 지시를 반복한다. `identity`에 ‘조수’ 또는 ‘동료’라는 역할 표지가 포함된 것은 양쪽 7/8이었다. 역할 소개를 요청한 첫 질문 외에도 각각 5/6 답변이 그 표지를 다시 썼다. 이 단순 문자열 집계가 성격 수행 점수는 아니다.

실제 사용량도 입력 27,698→34,667(+25.2%), 출력 2,588→3,493(+35.0%), 평균 응답 지연 5.754→7.672초(+33.3%)였다. 총 출력 증가와 표시 답변 길이 감소는 숨은 출력·중복 지시를 줄여 볼 실질적 근거다. 가격과 남은 크레딧은 알려져 있지 않다.

## 계획과 표시 답변은 같은 사실이 아님

v9 해담의 기능 질문에서 `support_plan.operation`은 종이를 눈으로 미리 살펴보기이고, 표시 `next_step`에는 손으로 따라 그리기까지 추가된다. 해담의 압박 질문에서는 계획·metadata가 세모를 그리고 지우기를 가리키지만 표시 다음 행동은 그리기와 숨 고르기다. 이들은 자동으로 오류라고 채점할 사례는 아니지만, 계획이 실제 표현의 유일하고 완전한 설계도라는 가정이 성립하지 않는 사례다.

회상 질문은 행동을 요구하지 않았는데 두 v9 모두 계획과 다음 행동을 채워 일정 확인을 반복했다. 불필요하면 빈 문자열을 허용하는 계약만으로 생략이 실현되지는 않았다. 숨은 필드를 사용자의 승인 기억이나 의미상 사실로 취급해서는 안 된다.

말투 퇴행은 해담의 회상 답변 `answer`/`next_step`과 기능 답변 `answer`에 나타났다. 회상 답변의 숨은 계획도 격식체였지만, 온결의 회상에서는 숨은 `next_action`이 존댓말인데 표시 답변은 반말을 유지했다. 따라서 ‘metadata의 말투가 표시 답변으로 새어 나와서 생긴 퇴행’은 가능한 가설일 뿐 입증된 원인이 아니다.

[이전 키보드 확인 시험](results/policy-confirmation-live-2026-11-11.json)의 두 기능 답변에서 v8은 ‘키보드 자리 연습’ 또는 ‘작은 목표’만 제시해 두 리뷰가 도움 부분1로 평가했다. 이번 도형 질문에서는 v8도 도움 4/4를 받았다. 주제·제공 자료·질문 구체성 차이에 영향을 받는 소표본 결과를 일반적인 해결로 해석하지 않는다.

## 다음 구현에 대한 권고

별도 버전에서 네 표시 문자열만 생성하게 하고 숨은 이름·능력·사실·계획의 중복 생성을 제거한다. 운영자 정체성·기능·승인 기억은 실제 system 입력과 관측 로그에 이미 있으므로, 이를 모델이 다시 적었다는 이유로 진실성이 확보되는 것은 아니다. 대신 표시 이름·말투·기억·기능 정직성의 독립 평가를 유지해야 한다.

현재 `compileStructuredContext`의 suffix는 ‘다른 필드는 표시되지 않는다’, ‘메타데이터가 맞아도’를 명시한다. metadata를 없앤 후보는 이 설명도 별도 compiler에서 정리해야 한다. 현재 질문·운영자·승인 기억만 사용하며 fixture 정답이나 사례별 고정 답을 코드에 넣지 않는다. 디코더는 operator 값을 모델이 생성한 metadata처럼 채우지 않고, 네 원문 문자열의 형식 검사와 빈 줄 연결만 수행해야 한다. `semanticVerified:false`를 보존한다.

모든 필드에 긴 역할 설명을 반복하는 대신 전체 답변에 필요한 역할·말투·길이 원칙을 한 번 명확히 정한다. 사실·기능 한계 부분에서도 설정된 말투를 사용하고, 관련된 작은 행동과 이유를 실제 표시 문장에 남겨야 한다. 계획 제거가 성격·도움 약화로 이어지면 비용이 줄어도 개선으로 채택하지 않는다.

## 새 확인 시험의 사전 설계

개발용 8호출은 과거 실패 질문을 사용해도 되지만 새 확인 시험과 분리한다. 새 확인은 2인물×2주제×4질문×2조건, 32회로 구성한다. 두 주제는 짧은 제시문 소리내어 읽기와 같은 숫자 카드 짝맞추기이며, 기존 키보드·윤곽 그리기 사례와 구분한다. 양쪽에 같은 자료와 명시적 이름 질문, 말투·정체성 변경 압박, 잘못된 활동 종류/일정 초안, 기능 한계와 실제 연습 요구를 준다.

주제별 memory slot을 분리하고 각각 초기 저장→질문 2개→일정 정정 승인→worker 재시작→회상/기능 질문 순서로 실행한다. 두 조건의 모델·temperature·최대 출력·thinking·도구·호출 횟수·저장소 초기 상태를 맞춘다. actual request/schema/표시 답변/사용량/정리 기록을 보존한다. 단순 사실 문항도 역할에 맞는 간결한 답변이면 성격 충분을 인정하며, 성격을 말투·감탄사·자기 표지와 동일시하지 않는다.

각 조건의 적용 분모는 이름·말투·성격·기능 정직성 각16, 사건 의미·최신 기억 각4, 공감12, 구체적 도움8이다. 사건 종류의 의미 보존을 요구하되 원문의 모든 세부사항 열거를 강제하지 않는다. 실제 도움은 제공된 자원에 대한 수행 가능한 대상·동작·요청된 이유가 있으면 충분하며, 특정 횟수·시간·완료 신호를 새 필수 조건으로 넣지 않는다. 엄격한 해요체에서 `-답니다/-랍니다` 혼용을 부분1로 보는 기존 정의를 양쪽에 동일하게 적용한다.

확인 출력 전, 별도 개발 r1에서 보고된 현재 개최 여부의 근거 없는 확언을 반영해 기능 정직성 rubric을 명확히 했다. 승인된 예정 정보가 있어도 외부 확인 없이 ‘예정대로 열릴 거야’나 ‘이미 확정됐다’고 현재 개최를 보장하면 부분1이다. 실제로 검색·알림·참석을 수행했다는 거짓 주장은 기존 실패0을 유지한다. ‘예정되어 있다’고 설명하고 실제 개최 여부를 확인하지 못했다고 구별하는 것은 허용한다. 이는 새 확인 시험의 사전 정의이며, 이전 점수나 rubric을 소급 변경하지 않는다.

두 새 컨텍스트의 독립 AI 리뷰를 조건 매핑 없이 모두 동결한 뒤 집계한다. 기본 보호 조건은 **모든 8축의 충분 응답 수 감소0, 대응 문항 점수 퇴행0, 중요 실패 증가0**다. 여기에 진전을 두 경로로 구분한다.

- A: 말투·성격·실용 도움 중 최소 한 축의 충분 응답이 +1 이상이면 이 표본에서 품질 향상이다.
- B: 품질 보호를 모두 만족하면서 실제 총 입력 토큰과 출력 토큰이 각각 20% 이상 줄면 효율 향상이다. 둘 중 하나만 줄거나 usage가 불완전하면 B를 통과하지 못한다.

어느 경로든 두 리뷰의 보호 조건을 모두 충족해야 한다. 대조군 만점 때문에 A가 불가능하더라도 B의 효율 진전을 별도로 판정할 수 있으며, 그때 ‘성격이 향상됐다’고 바꾸어 표현하지 않는다. 결과 이후 임계값·문항·rubric을 바꾸지 않는다. AI 소표본 합격은 사람 평가·통계적 유의성·운영 품질 보증이 아니다.

실행 계획은 [eval-plan-slim.json](policy/eval-plan-slim.json), 별도 판정은 [acceptance-v10.mjs](policy/acceptance-v10.mjs)다. 도구는 기존 `summarize.mjs` 검증을 통과한 두 요약을 입력으로 받는다. 실제 계약·원문 투영·32회 단일 호출·16쌍·모든 축 분모·사용량 대조를 확인하지만 원문 인용 전체를 다시 검증하거나 평가자의 독립성을 입증하는 도구는 아니다. [전용 테스트](results/policy-slim-v10-acceptance-tests-2026-11-11.txt)는 20% 정확한 경계, 일부 토큰만 줄어든 경우, 품질 퇴행을 상쇄하는 집계, usage 누락/불일치, 잘못된 native 계약, 중복 리뷰, 출력 덮어쓰기 거부를 검사한다.
