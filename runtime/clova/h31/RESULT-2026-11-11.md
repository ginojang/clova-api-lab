# H31 세 실행기 실제 비교 — 2026-11-11

Elda CLI native loop·LangGraph·memory-lab Pi를 동일 HCX-005와 artifact 도구로 실행했다. 기존의 “H31 미수행” 상태에서 실제 동일 과제의 원시 요청·응답·파일 판정까지 확보했다. LangGraph·Pi의 첫 거절 뒤 후속 도구 실행 문제도 수정했다. 운영 배포나 기준선 승격은 하지 않았다.

## 구현과 동등성

- Elda는 설치된 `LoopAdapter`와 `events.run`에 명시적 프로필을 넣는다. 새 모델 루프를 작성한 것이 아니며, 설치 CLI·자매 저장소는 변경하지 않았다. Comms·Notion·운영 장비 조회 도구는 비교에 포함하지 않았다.
- Graph/Pi에 명시적 비교 설정을 추가해 정확한 공통 system, raw artifact 이름/schema, MCP text 결과를 맞췄다. Pi의 일반 persona/기억 경로는 유지하며 비교 프로필에서만 우회한다.
- H40: 첫 거절은 같은 응답의 나머지 승인을 묻지 않고 실행하지 않으며, 모델 재호출 없이 denied로 끝낸다. call/result 쌍과 sideEffect를 보존한다. Pi는 SDK가 차단 호출에도 tool_call을 낼 수 있으므로 이벤트 개수 대신 실제 MCP 전달·sideEffect·파일을 확인한다.
- 한 턴 토큰 상한은 알려진 사용량을 다음 요청 전에 검사한다. 단일 응답의 초과까지 사전 예측하지 않는다. Graph도 이 시점으로 맞췄으며, 이미 수행한 파일 효과를 보존하고 다음 요청을 차단하는 회귀를 통과했다.
- 모의 공급자에서12세션·18턴을 실행했다. 모든 fresh 세션의 첫 요청과 도구 실행 후 두 번째 요청이 세 실행기에서 동등했다. 거절 배치·모두 허용 배치는 모델이 정확히 두 호출을 반환하도록 고정했다. [최종 preflight](../results/h31-confirm-preflight-2026-11-11.json).

## 실험 뒤 별도 완료 필드 수정

실제 비교를 끝내고 소스 일치를 확인한 뒤 Pi의 `runCompleted`만 좁게 보정했다. 최초 도구 오류가 있어도 이후 정상 모델 stop으로 루프가 끝나면 `runCompleted:true`로 기록한다. `ok:false`, `endReason:tool_error`, `toolFailed:true`와 기존 최종 답변 억제는 그대로다. 정상 성공 턴의 기존 동작도 유지한다. 루프 완료와 도구 오류를 별개로 드러내는 변경이며, 실제 과제 성공을 모델 말만으로 판정하는 변경이 아니다.

이 후속 수정은 모의 read실패→write→read→stop, 거절·중단·한도·정상 교정 경로로 검증했다. **수정 후 실제 API 재호출은0회**다. 실제 보고서의 `runCompleted:false`를 수정하지 않았으며, 당시 Pi CLI SHA는 `f0e5eaf0926e3ba9c9353350205c5e3553fef4bf8ad843dd79098a33d7cca5ae`, 후속 SHA는 `86bd7c05b447e00540774ff4bf901b7e382472409b4b3f234f2574ff3b99d937`이다. 과거 preflight는 새 코드에 재사용할 수 없으며 재실행 시 새 preflight가 필요하다.

다음 순서는 Pi의 복구 뒤 `ok`·최종 응답 정책 정리, malformed 인자/coercion 비교, 공식 키트용 독립 드라이버 검증이다. 이번 `runCompleted` 보정만으로 복구 종료 계약 전체가 같아졌다고 주장하지 않는다.
