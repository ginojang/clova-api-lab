# H31 2차 사전 계획 — 속도 제한 혼입 줄이기

1차 결과·원래 판정과 코드는 그대로 보존한다. 1차에서 실제38호출 중42901이4회였으며, Elda/Graph의 파일 결과는 맞아도 추가 읽기 때문에 엄격 순서 판정이 실패했다. 이것을 소급 통과로 고치지 않는다.

2차는 별도 run-r2/verdict-r2 코드·모의 preflight·실제 결과 파일로 실행한다. 모델·system·도구·출력2048·턴6회·토큰20000·전체90회 상한·과제와 승인 결정은1차와 동일하다. 요청 시작 사이 최소6초를 외부 측정 proxy에서 기다린다. 원시 응답을 가공하거나 실패 요청을 proxy가 재시도하지 않는다. 실행기 자체 재시도는 그대로 측정한다. 같은 계정의 다른 작업 부하까지 통제한 실험은 아니다.

[NAVER 사용량 정책](https://guide.ncloud-docs.com/docs/en/clovastudio-ratelimiting)은 계정 단위 한도와 입력+최대 출력에 기반한 TPM, 응답의 rate-limit 헤더를 설명한다. 실제 키의 요금 유형을 추측하지 않는다. 2차는 지정된 rate-limit 숫자 헤더만 기록한다. 인증·기타 헤더는 저장하지 않는다.

판정 변경은 새 결과에만 적용한다. 필수 write2→undo1→read 순서는 유지하며 그 뒤 동일 도구의 추가 읽기는 허용하되 추가 write/undo는 실패다. recovery는 실패 read 이후 성공 write→read와 파일 내용이 필요하다. 승인 거절 이전의 모델 재요청 횟수만으로 H40 실패를 판정하지 않고, 거절 뒤 추가 모델 요청·승인·실행이 없는지 확인한다. 1차와2차 점수를 하나의 변경 없는 평가 점수로 합치지 않는다.

전달 전후 소스 해시 확인·원시 이벤트·call/result·파일 판정·정리·미보고 usage를 그대로 보존한다. 같은 사례의 재검증이며 독립 미공개 벤치마크가 아니다. 지연이 포함된 전체 시간과 API 요청 자체 시간을 구분한다. 소규모 한 블록 결과로 운영 승격하지 않는다.
