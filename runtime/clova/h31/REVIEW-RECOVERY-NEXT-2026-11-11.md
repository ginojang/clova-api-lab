# H31 recovery-next 독립 검토 — 2026-11-11

측정 당시 러너·판정기와 실제 실행 증거를 독립적으로 읽어 확인했다. 키 내용은 읽지 않았고 추가 외부 API 호출은 하지 않았다. 이 문서 외의 소스·원시 결과·아카이브는 이 검토에서 수정하지 않았다.

## 결과와 제한

실제 native Elda·LangGraph·Pi 모두 `not_found` → 정확한 `RECOVERED` 쓰기 → 같은 파일 재읽기 → 비어 있지 않은 최종 응답을 수행했다. 각 도구 호출에는 대응하는 승인 이벤트가 하나씩 있었고 결과보다 먼저 나타났다. 세 실행기 모두 최종 응답은 마지막 도구 결과 뒤에 나왔다. 따라서 이번 관측의 복구·응답 동작은 원시 증거로 확인된다.

다만 사전 프로토콜의 **요청 시작 간격 최소 6,000ms**는 완전히 충족하지 못했다. 원시 `forwardedAt`의 연속 차이 중 두 곳이 **5,999ms**였다. 허용 오차를 사후 추가하거나 전체 프로토콜을 통과한 것으로 해석하지 않는다. 원본의 `boundaryPass:true`는 당시 판정기가 검사한 경계의 결과이며, 모든 프로토콜 조건의 충족을 뜻하지 않는다.

| 확인 항목 | native Elda | LangGraph | Pi |
|---|---:|---:|---:|
| 실제 제공자 요청 | 4 | 4 | 4 |
| 승인·도구 결과 짝 | 3 | 3 | 3 |
| 원시 HTTP/서비스 성공 | 4/4 | 4/4 | 4/4 |
| 실제 workspace 파일 | recovered.txt 하나 | recovered.txt 하나 | recovered.txt 하나 |
| 파일 및 최종 read 내용 | RECOVERED | RECOVERED | RECOVERED |
| 마지막 도구 결과 이후 최종 text | 있음 | 있음 | 있음 |
| ok / runCompleted / toolFailed | true / true / true | true / true / true | true / true / true |
| policyRejected / endReason | false / completed | false / completed | false / completed |
| 원시 사용량 입력 / 출력 | 610 / 120 | 610 / 120 | 610 / 120 |
| 정상 프로세스 종료·그룹 정리 | 확인 | 확인 | 확인 |

승인 입력도 실제 도구 인자와 일치했다. 첫 read 결과는 `not_found`, write 결과는 9 bytes, 마지막 read 결과는 정확한 `RECOVERED`였다. `taskSucceeded`는 없으며, 터미널 error 이벤트·잘못된 JSONL·러너 오류도 없었다. 실제 workspace를 다시 읽어 추가 파일·디렉터리·링크가 없음을 확인했다.

총 외부 호출은 **12/18**, 원시 사용량 합계는 **입력 1,830 / 출력 360**, 누락된 입력·출력 사용량 호출은 **0**이다. 각 런타임의 입력·출력 합계와 일치한다. 금액은 unknown이며 보고되지 않은 캐시 사용량의 완전성을 주장하지 않는다. Pi 자체 `externalModelCalls:0`은 loopback 프록시에 대한 관측이며, 외부 호출 수는 전달 프록시의 12회 기록으로 판단한다.

실제 전달 간격(ms): `6000, 5999, 6001, 6001, 6000, 6001, 5999, 6000, 6001, 6000, 6000`. 미달 지점은 Elda 2→3, LangGraph 3→4 요청이다. 실행기별 턴 시간은 각각 20,529ms·22,715ms·22,774ms였다.

## 측정 당시 러너·판정기의 수정 권고

아래 항목은 소스 아카이브에 보존된 **측정 당시 구현**에 대한 지적이다. 후속 배포 소스의 수정이나 새 mock 검증을 이 측정의 러너에 소급 적용하지 않는다.

1. **live wire parity가 최종 통과 조건에서 빠짐.** 러너는 실제 첫 요청 일치를 계산하지만 `boundaryPass`와 live 종료 코드에 반영하지 않았다. 이번 원시 요청을 독립 비교한 결과 세 실행기 모두 일치했다. 이후 구현은 live parity도 명시적 필수 조건으로 사용해야 한다.
2. **최종 응답 위치를 검사하지 않음.** `judgeRecovery`는 어느 위치든 비어 있지 않은 `text`가 있으면 허용한다. 정상 preflight의 최종 text를 없애고 도구 실행 전 안내 문장만 넣은 메모리 내 반례도 통과했다. 이후에는 마지막 도구 결과 다음, 정상 `turn_end` 이전의 응답을 요구해야 한다. 이번 실제 기록은 이 순서를 충족한다.
3. **복구 사례에서 호출별 승인을 검사하지 않음.** preflight 이벤트에서 모든 approval을 제거한 메모리 내 반례도 통과했다. 이후에는 callId·도구·입력 일치, 고유 approvalId, 호출별 승인 하나와 결과 전 순서를 확인해야 한다. 이번 실제 기록에는 이 승인 근거가 모두 있다. 다만 JSONL에 승인 응답 자체가 별도 기록되지는 않으므로 응답 전송은 아카이브된 테스트 러너의 동작과 함께 해석한다.
4. **단일 타이머 대기로는 엄격한 최소 간격을 보장하지 못함.** `delay(lastForward + 6000 - Date.now())` 뒤 시계를 다시 확인하지 않아 이번에 1ms 부족한 구간이 발생했다. 이후에는 대기 후 목표 시각을 재검사하고 필요하면 다시 기다리는 방식이 필요하다. 이번 측정의 timing 조건 미충족은 그대로 남는다.

추가 정적 검토 사항: `outerDeadlineMs:120000`은 현재 `ready`와 `idle` 각각의 대기에 적용되어 프로세스 전체의 단일 절대 deadline은 아니다. 실제 관측은 제한 안에서 끝났지만 이후 러너는 절대 종료 시각을 공유하는 편이 정확하다. 또한 pacing 대기 중 연결이 닫히면 fetch 직전 다시 취소 여부를 검사해야 늦은 외부 전달을 방지할 수 있다. 이번 실행에는 중단·시간 초과가 없었다.
