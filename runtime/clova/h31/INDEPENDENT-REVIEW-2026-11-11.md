Pi는 최초 도구 실패를 기억한 채 실제 복구까지 실행한다. 마지막 모델 응답은 stop이고 파일·read도 맞지만, CLI는 `error{tool_error}`를 내며 최종 `text` 이벤트를 내지 않았다. r2의 pass는 산출물·필수 실행·정리 판정으로 설계됐으므로 이 원시 실패를 성공으로 재분류하지 않는다. 운영 UI/러너가 `ok`와 `runCompleted`를 보는 환경에서는 실질적인 동작 차이다. 수정한다면 새로운 코드·회귀·실행 기록으로 검증해야 한다.

## 오류·요금·시간·정리

두 번째 실제 요청41회 모두 HTTP200 및 정상 CLOVA 응답이었다. 429·기타 API 오류·gateway 차단·강제 종료·잘못된 JSONL·worker 오류는 관측되지 않았다. 모든 run은 exit0, processGroupClean=true다. 이 정리 판정은 runner가 종료 시 검사한 기록이며, 이 검토에서 과거 프로세스 상태를 다시 만들지는 않았다.

입력/출력 usage 미보고 호출은0이다. 캐시 사용량은 NAVER가 보고한 수치로 확정할 수 없으며 Elda는 `usageUnreported`로 드러낸다. Graph/Pi의 cache0을 측정된 무료 캐시 사용량으로 해석하지 않는다. 비용 출처는 unknown이며 실제 요금·크레딧 잔액을 조회하지 않았다.

전역 요청 간격을 약6초로 제한한 시험이다. 기록된 전송 시각의 최소 간격은5999ms였으며 타이머·기록 정밀도를 고려해야 한다. 총 실행은 UTC08:21:41~08:25:44 약243초였다. 실행 순서가 사례별 Elda→Graph→Pi로 고정됐고 지연에는 속도 제한 대기가 포함된다. Pi의 요청1회 절감은 이 표본에서 추가 read1회를 하지 않은 관찰이지, 하네스 자체 속도 우위나 통계적 비퇴행 증거가 아니다.
