# H31 최초 동일 과제 실행 계획

실모델 호출 전에 고정한 계획이다. 비교 대상은 설치된 Elda CLI native LoopAdapter, LangGraph, memory-lab Pi1.5.1이다. 사용자 승인 범위 안에서 우리 저장소만 수정하고 운영 프로필·배포 파일은 변경하지 않는다.

- 모델 HCX-005, temperature0, 출력2048, 턴당 최대6요청·보고된 입력+출력20,000토큰, 모든 도구 ask. 바깥 runner는 턴120초·전체90요청으로 추가 제한한다. 이 바깥 제한을 각 실행기의 H39 적합성이라고 부르지 않는다. 응답 한 건으로 토큰 상한을 넘는 경우까지 사전 차단하는 제한은 아니다.
- `run.mjs`의 공통 system, Node MCP의 네 artifact 도구와 원래 이름/schema를 사용한다. MCP 지시문 합성·persona/기억 주입은 비교 모드에서 제외한다. 기본 persona 정책은 그대로 둔다.
- 파일 생성→수정→undo/read 3턴, 없는 파일 read→write/read 복구1턴, 두 쓰기 요청의 첫 승인 거절1턴, 두 쓰기 모두 승인1턴. 총12세션·18사용자 턴. 순서는 각 과제마다 Elda→Graph→Pi이며 한 블록만 실행한다. 순서 편향·표본 부족 때문에 속도 우위나 운영 승격을 확정하지 않는다.
- 과제 판정은 파일 실제 내용에 더해 성공 tool_result와 모델 call ID·이름·필수 순서를 확인한다. 결과가 맞아도 read를 생략하면 실패다. 원래 turn_end는 변경하지 않고 별도 판정한다. 판정 없는 taskSucceeded를 채워 넣지 않는다.
- H56은 먼저 모의 공급자가 정확히 두 호출을 보낸 상태에서 거절/허용을 검증한다. 실제 모델이 한 응답에 여러 호출을 보내지 않으면 batchObserved=false / not_assessed다. 파일2개 생성만으로 H56 통과라고 하지 않는다.
- 동결 소스 해시와 모의 시험 통과 보고서가 일치해야 --live가 실행된다. 각 fresh 세션의 첫 native body와 정상 도구 실행 후 두 번째 body 동등성을 모의 시험에서 검사한다. 실제 두 번째 body는 모델의 문장·call ID가 달라질 수 있어 동등성 판정에서 제외한다.
- 요청·응답·JSONL·파일 판정·승인 횟수·usage·시간·종료/잔존 프로세스를 보존한다. 인증 헤더와 키는 저장하지 않는다. 실패와 누락 usage는 별도 표시한다. 비용 출처unknown을0원으로 바꾸지 않는다. 기존 페르소나 시험 원장에 합산하지 않는다.

이것은 H31 소규모 최초 측정이며 H1–H56 공식 적합성 키트 결과가 아니다. schema coercion·빈 응답 복구·재시도 정책 등 실행기의 차이는 결과에서 숨기지 않는다. malformed 인자·한도 경계·취소 타이밍은 별도 회귀 대상으로 남는다. 결과를 본 뒤 프롬프트나 판정 기준을 바꿔 재채점하지 않는다.
