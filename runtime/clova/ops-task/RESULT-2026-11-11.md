# host-watch-explain 원문 판정

**v1·v2는 현재 상태로 운영 system에 반영하지 않는다.** 수치 창작은 관측하지 않았지만, v1에는 근거 없는 설정 초기화와 사용자 능력 단정이 남고 v2에는 드라이버·펌웨어·리셋 권고가 늘었다. 인용을 프로그램이 붙이는 방향은 적절하나 모델의 무근거 해석·조치까지 해결하지는 않는다.

## 원문과 실행 범위

인프라가 mars에서 실행한 [Elda-Ops `31bab41`의 원문27개](https://github.com/ginojang/Elda-Ops/tree/31bab41f54aecaa928856fbf69dc439014a2425f/host-watch/eval/2026-11-11)를 읽었다. 자매 저장소를 갱신하지 않고 이 랩 `.local`에 별도 Git 사본과 읽기용 추출본을 만들었다. 원본 파일 해시는 두 리뷰에 기록했다.

- v0: 현재 등록 Task의 R·A·B·C 네 건, run88~91·피드27~30이라는 인프라 기록이 있다. R은 실제 과거 수집 입력, A/B/C는 합성 표시가 있는 회귀 입력이다.
- v1: system 보강, 기존 prompt 유지, A/B/C 세 건. v2: v1 system을 유지하고 prompt의 근거 칸·두 줄 형식을 보강, A/B/C 세 건.
- v1/v2는 `elda job _ai` 격리 실행이며 등록부·run 기록·피드 생성이 없다. R의 후보 대응 실행은 없다.
- v2의 추가3회는 원래 보강3건 뒤 인프라가 추가한 실험이다. 원래 계획에 소급 합치지 않는다.

| 묶음 | 완료 worker 턴 | 입력 토큰 | 출력 토큰 |

원문에 retry/error 이벤트는0개이며 각1턴·completed다. 인프라가 실제 공급자10회를 보고했고 이 기록과 일치하지만, snapshot에는 HTTP 요청 ID·직접 전송 원장이 없다. 이번 리뷰에서 새 CLOVA 호출은0회다. cacheRead/cacheWrite는 usageUnreported에 있어 실제0으로 단정하지 않는다. 금액은 미상이다.

처음 Comms 표는 사례별 usage가 잘못 연결됐다. 원문의 입력·summary·runId를 대조한 올바른 값은 **R189/60, A198/52, B201/94, C195/54**다. 인프라가 `0eafbe4a97`에서 grep 결과 순서 가정 오류를 인정하고 정정했다. 원본 로그를 고친 것이 아니다. v0 파일 첫 `#` 줄은 러너 실행 메타데이터이며 이를 worker JSONL 위반으로 세지 않았다.

원문 묶음에는 실제 v0 resolved system, DB run 행·피드 본문이 없다. SQL333과 같다는 실행자 보고, runId·feedId 목록과 worker 기록을 구분했다. 작은 합성 세 사례의 한 번씩 생성한 답으로 HCX-005 전체의 성능·통계적 개선을 주장하지 않는다.

## 인용을 프로그램이 붙이는 경로

처음 읽은 watch.py는 stdout에서 알림 원문을 먼저 출력하고 해석을 뒤에 붙였다. 개별 host-watch 피드는 알림을 게시하지만, 직접 host-watch-explain의 task-runner 피드는 모델 summary만 전달했다. 따라서 당시에는 모든 출력에 근거가 붙는다고 할 수 없었다.

이 지적 뒤 풀스택은 mini-api `1821958`의 `params` 수신·가림·보존과 `[입력] … → 해석` 표시를 구현했고, CLI `afb612f`와 라이브 배포를 `1711b4121e`에서 보고했다. 인프라는 `791f844791`에서 실제 과거 R을1회 재생해 **run96·피드35에 net/facts/alerts 원문과 data.params가 들어갔다**고 확인했다. 이는 담당 팀의 새 실행 보고이며 위10개 품질 원문에는 포함하지 않는다. 그1회 usage는 아직 이 랩에 제공되지 않았다.

따라서 이 스레드의 해당 운영 시험 공급자 호출 보고 합계는11회(품질10+출력 경로 확인1)다. H31 91회나 페르소나344회에 섞지 않는다. 구조적 근거 표시가 확인됐다는 보고와 v0/v1/v2 해석 품질 미달은 동시에 성립한다.
