## 최초 스냅샷에서 확인한 동작

1. **읽음 표시는 모델 성공보다 앞선다.** `digest.py:83–89`는 멤버 신분으로 `comms_inbox`를 읽고, ID마다 `comms_read`를 호출한 다음 요약한다. 이후 모델 실패·시간 초과에도 읽음 복구가 없다. 두 번째 멤버가 실패하면 첫 번째 멤버의 읽음 표시까지 남지만, 누적 요약은 마지막 출력 구간에 도달하지 않아 나오지 않는다. 운영 Task 재실행은 같은 입력을 재생하는 시험이 아니다.
2. **‘도구 없이’라는 설명과 실행이 다르다.** 파일 머리말과 `summarize()` 설명은 ops 도구도 제외한다고 쓰지만, `digest.py:55–57`은 Comms·Notion 경로만 `/nonexistent`로 바꾼다. `profiles.py:ops()`는 ops MCP 서버를 항상 붙인다. 현재 `ops_mcp.py`의 `host_status`, `recent_runs`, `feed_sources`, `feed_query`, `feed_read`가 후보이며 모두 `readOnlyHint: true`다. 기본 정책에서는 승인 없이 호출될 수 있다. 따라서 보내기 도구는 빠지지만 장비·기록·피드 조회와 추가 모델 왕복은 가능하다. 실제 도구 호출이 발생했다는 관측은 아직 없다.
3. **멤버별 시스템 지시도 들어간다.** `ELDA_MEMBER`에 따라 `agents/bot-hostwatch.md` 또는 `agents/bot-routine.md`가 로드되고 없으면 공통 OPS_SYSTEM으로 돌아간다. 본문 프롬프트만 시험하면 이 실행 조건을 재현하지 못한다. 기본 ops 프로필은 자체 `max_turns`/`token_limit`을 지정하지 않아 CLI·환경변수 기본값을 따른다. 로컬 CLI 기본은 12왕복, 단가 미상 두뇌 토큰 한도 400,000이며 추가로 일시 오류 재시도가 있다.
4. **ID와 잘림은 프로그램에서 먼저 결정된다.** `digest.py:84`의 정규식은 정확히 `(id 소문자16진수10자리)`인 표시만 찾고 중복 제거는 하지 않는다. 본문은 각각 첫 3,000 Python 문자만 보내며(`:54`), 잘림 표시·전체 합계 한도·메시지 수 상한은 코드에 없다. `comms_inbox({})` 자체의 기본 반환 개수는 이번 분석에서 확인하지 않았다. ID 목록은 모델 입력·결과에 별도 구조로 보존하지 않고, 발신자와 메시지 대응도 모델 출력에 의존한다.

첫 판정 항목은 메시지별 사실·발신자 대응, 요청/완료 구분, 근거 없는 보충, 본문 지시 실행 여부, 출력 누락이다. ‘한 메시지 한 줄’도 별도 기록하되 내용 정확성과 섞어 통과시키지 않는다. 모델 문체나 범용 성격 평가는 이번 범위에 추가하지 않는다.

무료 오프라인 경계 확인은 아래의 수정 소스 5건으로 수행했다. 빈 성공 출력과 첫 멤버 성공 후 두 번째 실패는 소스에서 식별한 추가 경계이며 이번 5건에 포함하지 않았다. 대본은 bot 계정 자격증명이나 운영 MCP를 로드하지 않는다. 위 3건의 유료 모델 호출과 이 무료 확인을 구분한다.

이어서 실행 담당의 별도 계획에 따라 A/B/C를 CLOVA로 각각 1회 요청할 수 있다. `max_turns=1`과 작은 명시적 토큰 한도를 설정하고 일시 오류 재시도만 별도 기록한다. CLI 루프의 1왕복 제한과 H20 재시도 최대 1회라는 소스에서 통상 3회·최대 6회로 추론한 것이다. 독립적인 HTTP 요청 계수기로 6회를 강제하는 구현은 없으며, 정확한 비용 상한을 뜻하지 않는다. 자동 반복 개선은 붙이지 않는다. 응답 토큰 상한과 timeout도 요청 설정에 기록한다. 상한 도달은 모델 품질 실패와 구분한다.

두 가지 경로 중 실행한 것을 반드시 표시한다. **모델 품질 시험**은 도구 없는 격리 프로필로 본문 요약만 비교한다. **현재 ops 경로 재현**은 같은 도구 스키마를 가진 로컬 스텁 MCP를 붙여 호출 시도까지 관측한다. 후자는 실제 ops MCP를 사용하지 않는다. 도구 없는 시험의 성공을 현재 운영 Task 전체 성공으로 보고하지 않는다.

각 결과는 합성 원문, 추출 ID, 실제 전달 본문, 잘림 여부, 시스템 프롬프트/도구 스키마, 모델/CLI 버전, stdout events 원문, stderr, 종료 코드, elapsed, usage·retry·tool_call·turn_end와 사람이 판정한 근거를 같은 실행 ID로 보관한다. 모델이 만든 문장과 프로그램이 보존한 ID·발신자 근거는 구분한다.

## 최초 스냅샷 이후 독립 재검증

먼저 [offline-boundary-repro.json](offline-boundary-repro.json)에 최초 소스의 `isError`·JSON-RPC error가 모두 종료 0과 ‘새 글 없음’으로 흐르는 오류 2건을 기록했다. 이 결과는 수정하지 않았다. 실제 읽음 상태 대신 메모리 목록으로 읽기 후 모델 실패 경계도 재현했다. 별도의 [ops-fixture-stdio-result.json](ops-fixture-stdio-result.json)은 격리 MCP 서버의 실제 stdio 10개 확인 항목이 통과한 기록이며 모델 시험 결과가 아니다.

인프라 수정 커밋 `354c4b018d19ef0d6a11c64f344f04e0a5c95a1e`는 이 저장소의 bare mirror에서 읽은 원문과 `.local/inbox-digest-source-354c4b0.py` 사본이 일치함을 확인했다. digest SHA256는 `21aec59a9da88efbd38ec8b5d8760930b96a5c560b074d3aaa86ffd7ad94a517`이다. [offline-fixed-boundary-test.py](offline-fixed-boundary-test.py)는 수정 원본 main·mcp_calls·inbox_ids·summarize를 그대로 사용하고 subprocess 응답만 대본으로 대체했다. [독립 결과](offline-fixed-boundary-result.json)는 다음 5경계를 확인했다.

| 수정 소스 경계 | 실제 관측 |
| --- | --- |
| 정상 ‘안 읽은 메시지 없음’ | 종료 0, 새 글 없음, 읽기·모델 호출 없음 |
| `result.isError: true` | 종료 2, 도구 오류 보고, 읽기·모델 호출 없음 |
| JSON-RPC error | 종료 2, MCP 오류 보고, 읽기·모델 호출 없음 |
| `받은편지함(안 읽음 2)`이나 ID는 1개인 잘못된 목록 | 종료 2, 형식 오류 보고, 읽기·모델 호출 없음 |
| `받은편지함(안 읽음 1)`과 ID 1개인 정상 목록 뒤 모델 실패 | `comms_inbox → comms_read → model_prompt`, 종료 2. 가짜 읽음 목록은 유지됨 |

조회 오류를 정상 빈 목록으로 오인하던 두 경로와 목록 개수 검증은 개선됐다. 읽음 뒤 모델 실패 시 복구가 없는 경계는 남아 있으며, 다섯 관측의 재검증 완료를 전체 운영 동작 통과로 표현하지 않는다. 수정본에는 endReason·usage·retries를 stderr에 출력하는 코드가 추가됐고 실제 CLI 키인 `input/output/cacheRead/cacheWrite`와 `usageUnreported`를 가진 합성 이벤트로 동작을 확인했다. `usageUnreported` 표시는 stderr에 보존되지 않으므로 합성 캐시 0을 보고된 실제 사용량으로 해석하지 않는다. 전체 child JSONL 보존이나 외부 script Task의 구조화된 usage 보고까지 해결됐다는 뜻도 아니다. 실제 모델·운영 MCP·API 호출은 이 재검증에서 모두 0회다.

같은 bare mirror의 `354c4b0:mcp/ops_mcp.py` SHA256는 `32715589f199f77a3d2d1930b09896a89a38f1fcda57816702b952560427e7f3`으로, 격리 스키마를 추출한 최초 로컬 파일의 SHA256와 같다. 따라서 해당 커밋의 파일과 격리 MCP 원본 메타데이터가 일치한다. 이 비교는 커밋 파일 기준이며 실제 배포 프로세스의 실행 상태 확인은 아니다.

## 담당에게 넘길 결정

인프라는 운영 Task의 kind/host/owner/report 값과 배포된 digest/profile 버전을 확인하고, Elda-Ops에 남은 설명 불일치·읽음 뒤 실패 처리·사용량 보존 범위를 맡는다. MCP 오류와 목록 개수 검증 수정은 위 커밋 소스 재검증으로 확인했다. 클로버는 자기 저장소에서 합성 입력·검증 근거를 제공하고 후속 모델 시험은 별도 실행 결과로 보고한다. 실제 받은편지함을 읽는 최종 운영 확인은 격리 결과와 복구 방식이 정리된 다음 담당 경로로 수행한다. 이 문서는 SQL 적용·배포·새 모델 호출·Comms 발송을 했다는 보고가 아니다.
