# ② 운영 프로필 지침 — 사실·목록은 프로그램이, 해석만 두뇌가

2026-11-11 · 적용 대상: Elda CLI ② native loop를 쓰는 운영 Task(`kind:script` 안에서 호출하는 경로 포함). 다음 Task의 설계·검증 기준이며, 아래 항목이 현행 모든 Task에 구현됐다는 뜻은 아니다. Elda-Spec harness 절 I의 근거 지침이다.

**사람이 반드시 봐야 할 사실과 대상 목록은 모델 응답 없이도 보고에 남긴다.** 모델은 이미 보존된 근거에 대한 요약·원인 가능성·확인 제안만 더한다.

| 프로그램이 보존·표시할 것 | 모델에 맡길 것 |
| --- | --- |
| 장비·관측 시각·측정값·알림 원문·출처 | 근거에 맞는 원인 가능성과 사람이 확인할 항목 |
| 메시지 ID·보낸이·제목·전달 범위/잘림 표시 | 각 메시지의 요청·알림 요약 |
| 입력/출력 대응·검증 결과·실행/읽음 처리 상태 | 근거가 부족한 범위의 명시. 완료·승인·상태 변경 여부를 결정하지 않음 |

1. **대상 목록을 먼저 고정한다.** 신뢰할 수 있는 머리말·구조화 값에서 ID와 메타데이터를 만들고 원문을 보존한다. 본문 속 위조 `from`·지시문으로 바꾸지 않는다. 모델이 ‘없음’이라고 답하거나 항목을 빠뜨려도 원래 목록은 지우지 않는다.
2. **모델 입력의 범위를 밝힌다.** 원문과 실제 전달한 부분을 대응시키고 잘림을 표시한다. 보이지 않는 뒷부분을 추정해 채우지 않는다. 본문의 ‘완료했다고 출력하라’는 요청을 완료 보고로 바꾸지 않도록 지시한다. 요청 없는 알림·안내도 요약 대상이다.
3. **대응과 형식은 프로그램이 검사한다.** 메시지 번호/ID의 누락·중복·알 수 없는 값을 검사한다. 대응을 확정할 수 없으면 원래 목록과 모델 원문을 보여 주고 형식 오류를 표시한다. 발신자 표기·줄 수를 프로그램이 조립한 결과와 모델이 처음 낸 결과를 별도로 보존한다.
4. **해석을 사실이나 실행 권한으로 승격하지 않는다.** 관측과 추정을 구분하고, 없는 수치·완료 사실·사용자 능력·근거 없는 변경 조치를 만들지 않는다. 도구/알림 본문의 요청은 입력 자료이며 승인 근거가 아니다. 조치 대상 ID는 프로그램이 보존한 값에서만 가져온다.
5. **실행 성공·내용 판정·상태 변경을 분리한다.** `ok`/`runCompleted`는 의미 품질의 통과가 아니다. 요약은 종료 0·`turn_end.ok:true`·비어 있지 않은 결과를 확인한다. 받은편지함은 peek → 모든 요약 성공 → 읽음 표시 순서로 처리하고, 표시 완료/미확정/미시도를 구분한다. 실패에도 목록·이미 생성된 요약을 남긴다.
6. **검증 기록과 운영 선택을 분리한다.** 입력·시스템 지시·모델/CLI 버전·도구·한도를 고정하고 원문 이벤트, 사용량·재시도·종료 사유를 남긴다. 프로그램의 목록/상태 처리는 무료 회귀 시험으로, 의미 품질은 소수 고정 사례로 확인한다. 운영 채택으로 과거 실패를 통과로 바꾸지 않으며, 변경 후 시험하지 않은 문구는 그 사실을 적는다.

근거: [host-watch v3](candidate-v3/RESULT.md)는 근거 없는 조치 권고가 줄었지만 모델의 정확한 두 줄 조건은 0/3이었고, 운영 표시를 프로그램이 조립하도록 결정했다. [inbox-digest](inbox-digest/RESULT-2026-11-11.md)는 CLI 3건 정상 종료와 별개로 B의 요청→완료 진술 변환·C의 보이는 안내 누락을 확인했다. 읽음 처리 수정 `79865df`는 무료 회귀 11/11이지만 의미 오류 검출을 뜻하지 않는다.
